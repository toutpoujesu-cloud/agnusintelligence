Securing AI Agents: Tool Permissions, Sandboxing, and the Principle of Least Privilege

AI agents that can take actions — call APIs, execute code, access databases, send email — create a fundamentally new security attack surface. The same properties that make them useful make them dangerous if compromised or misdirected. This article explains how to apply security principles developed for privileged software systems to agentic AI.

The EU AI Act's robustness requirements (Article 15) and NIST's AI RMF (Govern 1.6, Manage 2.4) both require that AI systems operating with extended capabilities be designed to limit the potential impact of failure or misuse. For agentic AI, this translates directly to tool permission design and the principle of least privilege — the agent should have exactly the access it needs and no more.

The agentic AI attack surface

A conversational AI that only generates text has a limited attack surface: the worst outcome of a prompt injection attack is a harmful or misleading text output. An AI agent that can take actions has a dramatically larger attack surface: a successful prompt injection attack could cause the agent to exfiltrate data, send unauthorised communications, modify or delete records, execute malicious code, or make financial transactions.

The attack surface of an agentic AI system has four dimensions:

Dimension 1
Tool access
Every tool the agent can call — file system, database, API, email, code executor — is a potential exploitation vector. The broader the tool access, the greater the potential damage from a compromised or misdirected agent.
Dimension 2
Content processing
Agents that process external content — documents, emails, web pages, code — are vulnerable to indirect prompt injection: malicious instructions embedded in the content that redirect the agent's behaviour. Every external content source is a potential injection vector.
Dimension 3
Multi-agent delegation
When agents orchestrate other agents, permissions and trust can propagate through the delegation chain. A compromised sub-agent can attempt to acquire permissions beyond its scope by impersonating the orchestrator or by fabricating outputs that trigger privileged actions in the parent agent.
Dimension 4
Persistence and memory
Agents with persistent memory can be made to store malicious instructions that affect future behaviour — a form of persistent prompt injection. Every memory write is a potential attack on the agent's future behaviour.

Applying the principle of least privilege to AI agents

The principle of least privilege — a fundamental principle of secure system design — holds that every component should have access only to the resources it needs to perform its defined function, and no more. Applied to AI agents:

  • Per-task permissions, not session-wide permissions. An agent assigned to summarise a document should not have write access to the database. Grant permissions for the specific task, revoke them when the task is complete.
  • Read before write, write before delete. Privilege escalation within a session should require explicit human approval. An agent should not be able to upgrade its own permissions.
  • Scope permissions to the minimum necessary resource. If an agent needs to read one table, it should not have access to the entire database schema.
  • Time-bound permissions. Permissions granted for a task should expire when the task ends, not persist indefinitely in the session context.

The principle of least privilege directly maps to the EU AI Act's requirement for human oversight mechanisms (Article 14) and to the NIST AI RMF's Govern function, which requires establishing "policies, processes, and procedures for AI system oversight."

Tool permission design

Tool permission design is the practical implementation of least privilege for agentic AI. The goal is to make the permission system explicit, auditable, and aligned with the agent's defined mission.

A well-designed tool permission system for an AI agent distinguishes between:

Permission levelDefinitionAppropriate forHuman approval required
READ Access information, no modification Research tasks, context gathering, document analysis No (unless sensitive data)
SUGGEST Draft an action for human review; does not execute Email drafts, code proposals, data modifications Yes — human reviews before execution
ACT (bounded) Execute within a defined, limited scope Routine, reversible, low-risk operations No, if within defined scope and reversible
ACT (unbounded) Execute with broad or irreversible effects Financial transactions, production deployments, data deletion Yes — mandatory for all irreversible actions
SYSTEM Modify permissions, system configuration, or agent parameters Never granted to AI agents N/A — agents must not be able to modify their own permissions
Design principle

The critical rule: an AI agent must never be able to grant itself higher permissions than it was assigned. Any action that would increase the agent's own authority requires a human approval step — an agent requesting permission escalation is itself a signal worth investigating.

Sandboxing agentic AI systems

Sandboxing is the practice of isolating a process from the systems it could affect, limiting the blast radius if something goes wrong. For agentic AI, sandboxing operates at multiple levels:

Network isolation

AI agents should not have unrestricted network access. In most deployment contexts, an agent's outbound connections should be limited to a defined allowlist. An agent that can make arbitrary outbound network connections can exfiltrate data, establish command-and-control channels, or interact with services outside its defined scope.

Code execution environments

Agents that can execute code — a capability increasingly common in commercial AI tools — must execute in isolated environments with no access to host system resources, production data, or credentials. Code execution sandboxes should enforce: time limits, memory limits, no filesystem persistence beyond the task, no outbound network by default, and no access to environment variables or secret stores.

Content processing isolation

External content (documents, emails, web pages) processed by an AI agent should be handled in a context that is clearly separated from the agent's instruction context. This reduces the effectiveness of indirect prompt injection by making it harder for injected instructions in content to reach the model's instruction-following pathways.

The governance layer for agentic AI security

Technical controls — least privilege, sandboxing, permission matrices — are necessary but not sufficient. They must be supported by a governance layer that makes permissions explicit, auditable, and human-reviewable:

  • Mission Contracts. Every AI agent deployment should have a documented Mission Contract specifying: the agent's purpose, its permitted tool access, the conditions under which human approval is required, and the evidence requirements for audit. This is the governance equivalent of a service account access policy.
  • Immutable audit logs. Every agent action that crosses a system boundary — reads a protected resource, calls an external API, executes code — must be logged with enough detail to reconstruct the event. Logs must be immutable and stored outside the agent's own context.
  • Human approval gates for consequential actions. Actions with irreversible effects — sending external communications, modifying production data, deploying code — require a human approval step with a time-bound, single-use approval token. The agent cannot execute the action before the approval is granted, and cannot reuse the approval for a different action.
  • Anomaly detection. Monitor agent behaviour for deviations from expected patterns: unusual tool call sequences, requests for resources outside the mission scope, repeated attempts to escalate permissions. These are signals of either compromise or misuse.

Regulatory basis

The EU AI Act's requirements for high-risk AI systems — robustness (Article 15), human oversight (Article 14), and technical documentation (Article 11) — all apply with heightened force to agentic AI systems with tool access. The Commission's guidance on Article 50 transparency requirements also implies that users interacting with agentic AI should be informed of the system's capabilities, including its ability to take actions on their behalf.

NIST AI RMF's Govern 1.6 explicitly addresses "risk tolerance and risk appetite" for AI systems that can "take actions that affect the environment" — the primary reference point for tool-using agents. The Manage function's requirements for impact assessment and residual risk management apply to every tool the agent can call.
