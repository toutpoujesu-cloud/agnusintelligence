Excessive Agency: When AI Agents Are Given Too Much Permission

Excessive agency does not require an attacker. It occurs when an AI agent is given more capability, permission, or autonomy than its task requires — and then uses that capability in unintended ways during normal operation. It is one of the most common sources of serious AI incidents in production, and one of the most preventable.

Jean-Daniel Alexis· 11 September 2026· AI Security pillar· AR-000570

What excessive agency looks like in practice

The OWASP Top 10 for Large Language Model Applications names Excessive Agency (LLM06) as one of the top ten risk categories because it is both common and consequential. The pattern is straightforward: a developer builds an agent to perform task X, gives it access to everything it might conceivably need, and deploys it. The agent then uses that access in ways the developer did not intend — not because of malicious manipulation, but because an LLM does not share the developer's assumption about what the agent is supposed to do.

Real production examples include: customer service agents that delete records when asked to "remove" a complaint; email assistants that forward sensitive information to contacts they infer from context; coding agents that commit directly to main branches because they have write access; finance agents that approve transactions above the intended threshold because the approval logic was too permissive.

What makes excessive agency particularly dangerous is that it amplifies other vulnerabilities. A prompt injection attack delivered through an email achieves nothing if the email assistant cannot send emails, access external URLs, or modify contacts. Give the agent all three capabilities and the same injection becomes a serious incident.

The root causes

Cause 1
Overly broad tool access
The agent is given access to a full API rather than the specific endpoints its task requires. A customer service agent that needs to read order status is given full database access. A coding agent that needs to write to a feature branch is given repository admin rights.
Cause 2
Missing action constraints
The agent's task is defined by what it should do, not by what it should not do. Without explicit prohibitions, the agent may take actions that seem logical to it but were never intended — deleting data to "clean up," forwarding information to "help," modifying configurations to "optimise."
Cause 3
Autonomy misconfiguration
The agent is given a higher autonomy level than its task requires. A task that should be A2 (human-confirmed for exceptions) is deployed at A3 (human-monitored) or A4 (human-informed). The gap between intended and actual autonomy level is the excessive agency.
Cause 4
Inherited permissions
The agent runs under credentials that have more permissions than the agent needs — because the credentials were created for a human user or a different system, and reused for convenience. The agent inherits permissions it was never intended to have.

The least-privilege principle applied to AI agents

The least-privilege principle — give any system the minimum permissions required to perform its function, and no more — is a foundational security principle that applies directly to AI agent deployments. Applied to agents, it means:

Capability scoping: An agent's capability set should be derived from its task, not from what is technically available. If the task is to read and classify emails, the agent needs read access to the email inbox. It does not need send access, contact access, or calendar access — even if those capabilities would "make it more helpful."

Action-level permissions: Permissions should be granted at the action level, not the resource level. "Access to the payments system" is not a permission — "read from invoices table" and "write to payments_draft table, rows where status = pending" are permissions.

Credential isolation: Agents should run under credentials created specifically for them, not credentials shared with humans or other systems. This prevents permission inheritance and makes it possible to revoke the agent's access without affecting other systems.

Time-bounded permissions: Permissions should expire. An agent that is deployed for a three-month project should have permissions that expire when the project ends, not permanent credentials that remain active indefinitely.

Controls for excessive agency

ControlWhat it preventsImplementation
Mission Contract with explicit prohibitions Actions outside intended scope Document both allowed capabilities and explicit prohibitions. Prohibitions should be specific action types and resources, not general principles.
Capability minimisation review Overly broad tool access Before deployment, audit each capability in the agent's tool set. For each capability, ask: "Can the agent complete its task without this?" Remove capabilities that are not essential.
Agent-specific credentials Permission inheritance Create dedicated credentials for each agent with only the permissions that agent needs. Never reuse human or system credentials for agent deployments.
Pre-execution policy check Out-of-scope actions at runtime Every consequential action is evaluated against a policy engine before execution. The policy engine enforces the Mission Contract in real time — it does not rely on the agent's judgement about whether an action is within scope.
Anomaly-based monitoring Unusual action patterns Establish a baseline of normal agent behaviour and alert when the agent accesses resources, takes actions, or achieves throughput outside the baseline. Excessive agency often manifests as volume anomalies before it manifests as harmful outcomes.
