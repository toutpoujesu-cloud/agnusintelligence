AGNUS Academy Level 8 · Foundation L8-02 — Agent Architecture Patterns
Step 1 of 4 — Understand4 min

The Plan → Act → Observe loop from L8-01 comes in several named shapes.

Every real agent framework is a variation on that same closed loop — but how it reasons before acting, whether it double-checks itself, and whether it's one agent or several, differs by pattern. Knowing the names lets you recognize which one you're actually working with.

Why this matters

Choosing the wrong architecture pattern for a task is a common, costly mistake — a single ReAct agent trying to do what really needs a Reflection step will confidently ship a first draft as if it were final. Recognizing the pattern in use tells you what kind of failure to watch for.

Step 2 of 4 — See5 min

Four architecture patterns — click each to see how it actually runs

Reason → Act → Observe → Reason → ...

The base pattern from L8-01, made explicit: the model reasons in words about what to do, takes one action, reads the result, and reasons again. Simple and transparent — you can read its reasoning at every step — but it never steps back to critique its own overall approach.

Act → Self-critique → Revise → Self-critique → ...

After producing a full attempt, the agent generates a separate critique of its own work — checking for gaps, errors, or unmet requirements — before revising. This catches issues that ReAct's step-by-step reasoning alone tends to miss, because it evaluates the whole output at once, not just the next immediate action.

Agent A (research) → hands off → Agent B (writing) → hands off → Agent C (review)

Different agents, each specialized for one part of the task, coordinate by passing work to each other — echoing the handoff-loss risk from M14, but at the agent level instead of the tool level. A weak handoff here has the exact same failure mode: something true and important can get dropped between agents.

Step 1 (fixed) → Step 2 (fixed) → Step 3 (fixed)

A predetermined sequence of steps, not decided dynamically by the model at runtime. More predictable and easier to audit than the other three patterns, but it can't adapt if a step's actual result doesn't match what the fixed sequence assumed would happen.

AReAct — because it reasoned about what to write.

CMulti-Agent — because more than one step was involved.
DWorkflow — because contracts always follow a fixed legal structure.
EThis cannot be classified as any known pattern.

A pipeline runs the exact same three steps in the exact same order for every customer support ticket — categorize, draft reply, send for approval — regardless of what the ticket actually says. Which pattern is this, and what is its main limitation?

AWorkflow — predictable and auditable, but it can't adapt if a ticket doesn't fit the fixed sequence's assumptions.
BReAct — because it takes real actions on each ticket.
CReflection — because it involves a review step at the end.
DMulti-Agent — because three named steps are involved.
EThis pattern has no meaningful limitation, since the steps are fixed and therefore fully reliable.
