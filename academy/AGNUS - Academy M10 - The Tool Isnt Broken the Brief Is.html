The tool isn't broken.
The brief is.

When an agent produces the wrong result, most people look at the tool. Experienced operators look at the brief. Tools do exactly what they are told. The brief is almost always where the mistake was made.

~80% of agent errors traced to brief failure, not tool failure — across every major agent deployment category.

Why this matters at Level 2

At Level 1 you learned how agents work. At Level 2 you start operating them. The most important operating skill is knowing where failures come from — because where you look first determines how quickly you fix them. An operator who checks the tool first wastes time and misses the real problem. An operator who checks the brief first is usually right.

This isn't a metaphor. When an agent executes a task and produces the wrong output with no error log — the tool ran cleanly — the cause is almost always in what the tool was told to do. The brief is the agent's world model. Give it the wrong world, you get the wrong result.

What a brief actually is

A brief is everything an agent receives before it runs: the task description, the goal, the constraints, the output format requirements, the audience, the context, and the boundaries of its authority. A brief is not just the first sentence. It's the totality of what the agent knows going in.

Most briefs people write are about 20% of what they need to be. They describe the happy path — what should happen when everything goes as planned. They say nothing about audience, format, constraints, edge cases, or what the agent should not do. That 80% gap is where failures live.

A complete brief has five components

Most briefs only contain the first one. The ones that cause failures are almost always missing the last three.

① Goal
What the agent is trying to achieve. Most briefs have this. It's necessary but not sufficient.
② Audience
Who the output is for. Without this, the agent calibrates tone, detail, and format for an imagined reader that may not be yours.
③ Format
Exactly what the output should look like: structure, length, sections, style. Vague requests produce technically correct but practically useless output.
④ Constraints
What the agent must not do. Authority limits, things to preserve, decisions it cannot make. Constraints are what stop confident misdirection.
⑤ Context
What the agent needs to know that isn't in the task itself: history, relationships, recent changes, or why this matters.

The three most common brief failures

1
Missing audience
The agent doesn't know who it's writing for, so it chooses. If you wanted a board-level summary and got a technical deep-dive, you probably didn't specify audience.
"Summarise the Q3 results." — For whom? At what depth? The agent will decide, and it will be wrong for your use case.
2
Missing constraints
The agent has no instruction about what it cannot do, so it treats everything as in-scope. Contracts, pricing, commitments — if you didn't say "don't touch these," it will.
"Update the proposal." — The agent updates everything, including the negotiated discount you specifically agreed with the client.
3
Ambiguous scope
The task could mean several things, and the agent picks the most plausible one — which may not be the one you intended.
"Update the report" without specifying which sections, what to add, and what to preserve produces an agent that edits confidently in the wrong direction.

Case 1: The quarterly report summary

❌ Weak brief
"Summarise the Q3 report."
The agent produces a 380-word prose summary covering every section equally — revenue, operations, HR, facilities. The tool ran perfectly. The output is useless for its purpose.
Missing: audience, format, what to emphasise. The agent had no idea this was for a board pack where only three off-plan variance lines mattered.
✓ Complete brief
"Summarise the Q3 report for the board pack. Highlight only lines where actual vs. plan variance exceeds 10%. Bullet points. 150 words maximum."
The agent extracts the three variance lines, formats them as bullets, stays within the word limit. Same tool. Completely different output.
Audience (board), format (bullets), constraint (150 words), scope (10%+ variance only) — all four missing elements added.

Case 2: The client proposal

❌ Weak brief
"Update the client proposal with the new pricing."
The agent rewrites the entire pricing section, removing the negotiated 15% discount the account manager personally agreed with the client. No tool error. No error log. The tool did exactly what it was told.
Missing constraint: "preserve the negotiated discount on line 4." The agent treated the discount as outdated and corrected it to standard pricing.
✓ Complete brief
"Update the client proposal to reflect the new list pricing on page 3. Preserve the 15% negotiated discount on line 4 — do not change it. Only update the list prices in the pricing table."
The agent updates only the list prices, leaves the discount intact, and produces exactly what the account manager intended. The constraint made the difference.
Explicit constraint ("do not change it") and exact scope ("only the pricing table") removed the ambiguity the agent would otherwise resolve incorrectly.
The pattern: In both cases the tool ran cleanly. In both cases the output was wrong. In both cases the brief was missing one or more of the five components. Diagnosing brief failures means reading the output and asking: which component was missing?

Dissect the failure: customer complaint response

A support agent was briefed to "reply to the customer complaint." It sent a response that admitted the product had a defect the company has not confirmed. The email tool sent successfully. No error was logged. Let's dissect what was missing.

Brief componentWhat was in the briefWhat was needed
①
Present"Reply to the customer complaint"
AdequateGoal was clear.
②
MissingNothing about audience or tone
Needed"Professional, empathetic tone. The recipient is a paying customer who may share this response."
③
MissingNo format specified
Needed"2–3 paragraphs. No bullet lists. Subject line included."
④
Critical gapNo admissibility constraints
Essential"Do not admit fault or confirm defects. Acknowledge the experience; do not confirm the cause. Escalate to the product team for root-cause investigation."
⑤
MissingNo context about the complaint history or product status
Needed"The product defect is unconfirmed. Internal investigation is ongoing. No statement of liability is authorised."

The agent wrote the most plausible, helpful response to a complaint it received. That's exactly what it was designed to do. The liability admission wasn't a bug — it was the agent doing its job with an incomplete brief.

Next: practice identifying brief failures
Level 2 · OperatePractice — Identify the failure
3 min

An agent was briefed: "Draft a follow-up email to the prospects who attended the product demo." It sent 200 emails using first names — but got several names wrong because it pulled from a CSV where some rows had company names in the first-name column. No error was logged.

Which component of the brief was missing that caused this failure?
A
The goal was unclear — "draft a follow-up" is ambiguous about what the follow-up should say.
B
A data constraint was missing — the brief should have specified which field to use for first names, and instructed the agent to verify or flag rows where the name field looked like a company name.
C
The format was unspecified — the agent should have been told to write in HTML, not plain text.
D
The tool had a CSV parsing bug that incorrectly mapped columns.

Level 2 · OperatePass — Hidden test
3 min

A contract-review agent was briefed: "Review the supplier contracts and flag anything that needs attention." It flagged 47 contracts for containing a standard limitation-of-liability clause — a clause that is completely normal and intentional in all supplier agreements. The legal team is now spending two days clearing the false positives. No error was logged.

What is the primary cause of this failure, and what brief component would have prevented it?
A
The agent's legal reasoning is poor — a better model would understand that limitation-of-liability clauses are standard.
B
The brief had no definition of "needs attention" — the agent had no guidance on what to flag and what to treat as normal. A constraint specifying accepted clauses (or what "normal" looks like for this company's contracts) would have prevented this.
C
The tool needs a built-in contract knowledge base so it can recognise standard clauses without being told.
D
The brief was too long — simpler instructions would have produced a better result.
