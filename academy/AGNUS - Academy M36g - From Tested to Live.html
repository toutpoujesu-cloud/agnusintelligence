Tested locally is not the same as live in the real world.

Your app has passed every scenario on your machine. That's necessary, but it isn't the finish line — a real user needs a real URL, and going live changes what's actually at risk.

Why this matters

The same verification-first principle applies one more time: an agent saying "it's deployed" is not evidence until you've confirmed the live version actually behaves the way your tested version did. Deployment is not automatic proof that everything still works.

What changes between local and production.

Your machine is a safe, private environment. A live URL is public — and that changes what has to be handled correctly.

Local (your machine)
  • Only you can access it
  • Mistakes cost nothing but your own time
  • Secrets can sit in plain files
Production (live)
  • Anyone with the URL can access it
  • A mistake is a real user's real problem
  • Secrets must be stored as protected environment variables, never committed to the code

Ask the agent to name what needs to change

Before deploying, ask directly: "What in this app needs to change to go from running on my machine to running safely in production?" A good answer names environment variables, error handling for real users, and removing anything meant only for local testing.

Re-run the scenario list — on the live URL, not just locally

The scenario document you built in the last module doesn't retire once deployment happens. Run through it again against the real, public URL. A test that passed locally can still fail live — a missing environment variable or a misconfigured host setting can silently break something you already verified.

Keep a backup on your own machine, and also push it to GitHub — two independent copies, not one.
After every milestone that works, update both backups — don't wait until the whole project is finished.
If the app breaks or something fatal happens, you can revert to the last working milestone instead of losing everything.

Rollback discipline

Know how to roll back to the last working version before you deploy — not after something breaks.
If a scenario fails on the live URL, don't leave the broken version up while you investigate — roll back first, then fix.
Log the incident in your project's Logs document: what broke, what caused it, how it was fixed — the same discipline from The Protocol.
