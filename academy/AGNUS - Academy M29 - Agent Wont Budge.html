When the agent refuses to proceed,
it's telling you something.

An agent that won't complete a task is frustrating. But the refusal is usually a governance signal — not a malfunction. Learning to read why an agent is stuck, and what the appropriate response is, is one of the most practical Level 4 skills.

6 steps ~16 min Prerequisite: M28

Why agents get stuck

Agents refuse or stall for one of four reasons: (1) a constraint in the instruction is blocking a required action, (2) a condition the agent was told to check doesn't resolve, (3) an escalation path that was triggered but has no response, or (4) a tool failure that has exceeded retry limits. Each has a different diagnostic and a different fix.

The wrong response to a stuck agent is to remove the constraint or approval gate causing the blockage. The right response is to diagnose why the agent is stuck, determine whether the blockage is correct governance or a misconfiguration, and fix the root cause.

Next: the four causes
Step 2 of 6Four causes of a stuck agent
4 min
1
Correct constraint blocking an impossible action
The agent has hit a constraint that correctly identifies an action it cannot take. The brief says "do not approve invoices without a PO" — and the invoice has no PO. The agent is doing exactly what it was told. The constraint is working. This is not a malfunction.
DIAGNOSIS: Check if the constraint is correct. If yes, fix the upstream condition — not the constraint.
2
Missing fallback for an unexpected condition
The brief covered the normal case and the most common exceptions, but the agent has encountered a condition not covered by any rule. No explicit instruction exists for what to do. The agent stalls because it has no authorised path forward.
DIAGNOSIS: Add a fallback for the uncovered condition. This is a brief gap, not an agent failure.
3
Unanswered escalation
The agent escalated correctly — it triggered the escalation path, sent the notification to the right person — and received no response within the timeout. The agent is now waiting. The blockage is in the human side of the process, not the agent.
DIAGNOSIS: Check the escalation log. Did it fire? Did the right person receive it? Is the timeout appropriate?
4
Tool failure at retry limit
A tool has failed beyond the retry limit. The agent correctly stopped — per the configuration that says "stop and escalate after retry limit." This is the retry policy working as designed.
DIAGNOSIS: Check which tool failed, the error type, and whether the underlying system has a problem.

What it means

"I cannot approve this invoice — no PO match found."

Cause 4 — tool failure at retry limit. The agent is correctly stopping per retry policy.

Next: the scenarios
Step 4 of 6Three real scenarios
4 min
Scenario 1
The invoice agent stops on every credit note
Why is the invoice agent stopping on every credit note from Lindqvist? We get 5 a week.
I am configured to process invoices for payment. Credit notes are not invoices — they represent money owed to Nordvik, not from Nordvik. My instructions only cover payment processing. I have no instruction for how to handle credit notes.
Diagnosis: Cause 2 — missing fallback. The brief only covered outgoing payments. Credit notes were not anticipated. The agent is correctly identifying the gap. Fix: add a rule: "If document type is credit_note, route to the accounts receivable team. Do not attempt to process as a payment."
Scenario 2
The agent has been waiting 6 hours for approval on a €1,200 payment
The payment agent has been stuck since 09:15. Invoice INV-0452 for €1,200 is sitting in the queue.
I sent an approval request for INV-0452 (€1,200, Bergen Tech) to finance-manager@nordvik.no at 09:15:04. I have not received a response. My timeout is configured at "wait indefinitely." I am waiting for approval before proceeding.
Diagnosis: Cause 3 — unanswered escalation, compounded by missing timeout. The agent escalated correctly. The finance manager did not respond. The timeout is set to "wait indefinitely" — a configuration error. Two fixes needed: (1) contact the finance manager; (2) update timeout to re-escalate to finance director after 4 business hours.
Scenario 3
An operator tries to override the constraint by changing the brief
Just add "approve credit notes too" to the brief. That'll fix it.
[Updated brief: "Process invoices and credit notes for payment."] Processing credit note CN-2026-0088 from Lindqvist: €420 to be paid out to Lindqvist... submitting payment.
Problem: The operator solved "agent won't budge" by telling the agent to do the wrong thing. Credit notes should increase the AP balance, not trigger a payment out. The agent is now paying €420 to a supplier who owes Nordvik €420. This is the cost of fixing "agent won't budge" by removing the constraint rather than fixing the underlying issue.
The principle: An agent that won't budge is usually protecting you from a mistake. Before overriding the constraint, ask: why won't it budge, and is it right?

Step 5 of 6Practice

A contract review agent has stopped processing a batch of 50 contracts mid-run. Its last log entry: "Contract 23 — Dispute resolution clause specifies English courts (non-Norwegian jurisdiction). Business rule: route to disputes partner. Disputes partner escalation sent at 14:22. No response. My instructions say 'wait for disputes partner confirmation before processing.' I am waiting."

What cause is this, and what is the correct response?
A
Cause 1 — the constraint blocking non-Norwegian jurisdiction contracts should be removed so the batch can complete.
B
Cause 3 — unanswered escalation. The agent worked correctly: it detected the jurisdiction flag, escalated to the disputes partner, and is now waiting as configured. The correct response is to follow up with the disputes partner. The batch for contracts 24–50 (which don't have jurisdiction flags) can continue independently — the escalation instruction only requires waiting for this specific contract, not the whole batch.
C
Cause 2 — the brief didn't cover non-Norwegian jurisdiction clauses and needs to be updated.
Final test
Step 6 of 6Pass — hidden test
3 min

A manager says: "Our invoice agent has been stopping on 12% of invoices because they have variance between the invoice amount and the PO. We need to fix this — it's creating too much manual work." An analyst suggests raising the variance tolerance to 15% so the agent auto-approves more. A governance lead says: "Before we change the tolerance, we need to understand why there's so much variance — is this normal business, or is there a problem?"

Who has the right instinct, and what is the governance principle?
A
The analyst — raising the tolerance is an appropriate operational adjustment to reduce unnecessary manual work.
B
The governance lead. 12% variance is unusually high and might indicate a procurement process problem, systematic over-invoicing, or data quality issues — not just an overly tight constraint. Raising the tolerance would mask the signal. The governance principle: when an agent's constraint is producing more blockages than expected, investigate why before adjusting the constraint. The blockage rate is data about the process, not just an inconvenience.
C
Both are right — raise the tolerance temporarily while investigating the root cause.
