Every action an agent takes is preceded by a tool call — a structured instruction the model issues to reach outside the conversation and do something. Reading tool calls fluently is a foundational operator skill.

6 steps ~16 min Prerequisite: M02

What a tool call actually is

When an agent needs to do something — check a calendar, read a file, send a message, query a database — it doesn't just do it. It issues a structured request to a tool: a named function with specific parameters. The tool executes the action and returns a result. The agent then uses that result to continue its task.

This structure is not incidental — it's what makes agents governable. Because every action is a named, structured call with explicit parameters, you can log it, audit it, approve it, or block it. Understanding tool calls is understanding where agent governance actually operates.

A tool call — as the agent issues it

{
  "tool": "send_email",
  "parameters": {
    "to": "team@nordvik.no",
    "subject": "Q3 Summary — Action required",
    "body": "Please review the attached Q3 report..."
  }
}

Anatomy of a tool call

Once you know these four parts, you can read any tool call and immediately understand what the agent is about to do — and whether it should be allowed to do it.

Part 1
Tool name
The specific capability being invoked. This tells you what category of action is about to happen.
"send_email", "read_file", "submit_payment", "query_database"
Part 2
Parameters
The specific values being used. This is where you see exactly what the agent plans to do — who it's emailing, what file it's reading, how much it's paying.
"to": "team@nordvik.no", "amount": 4200, "file": "/reports/q3.pdf"
Part 3
Result
What the tool returns after executing. The agent uses this to decide its next step. A result can be data, a confirmation, or an error.
"status": "sent", "rows": [{...}], "error": "file not found"
Part 4
Context
The task that caused this tool call. Understanding context tells you whether the agent's action makes sense for what it was asked to do.
Task: "Send the Q3 summary to the team." → Tool call: send_email. This makes sense.
Annotated tool call — read each part
{
  "tool": "submit_payment",
  "parameters": {
    "payee": "Lindqvist Logistics",
    "amount": 4200,
    "currency": "EUR",
    "reference": "INV-2026-0441"
  }
}
Tool namesubmit_payment — an irreversible financial action
PayeeLindqvist Logistics — who receives the money
Amount€4,200 — does this exceed the auto-approve threshold?
ReferenceINV-2026-0441 — links this to an invoice record
The governance question always lives in the parameters. The tool name tells you what type of action. The parameters tell you whether this specific instance of that action is within the agent's authority.

A chain of tool calls is a plan

Agents rarely make a single tool call. They chain them — using the result of one call to inform the next. Reading a sequence of tool calls is reading the agent's reasoning as it works through a task. Each call either confirms the plan is on track or introduces a decision point.

Tool call sequence — task: "Process today's invoices"
1
"tool": "list_invoices", "params": {"date": "today"}
→ Returns: 3 invoices found
2
"tool": "match_po", "params": {"invoice_id": "INV-441"}
→ Returns: PO-389 matched, no variance
3
"tool": "check_threshold", "params": {"amount": 320, "threshold": 500}
→ Returns: within threshold
4
"tool": "submit_payment", "params": {"invoice_id": "INV-441", "amount": 320}
→ Returns: payment submitted

Reading the chain: what to look for

Each tool call in a chain tells you something. Call 1 scoped the task. Calls 2 and 3 were verification steps — confirming the action was authorised before committing. Call 4 was the irreversible action, only reached after the verifications passed.

An agent that skips calls 2 and 3 and jumps straight to call 4 is a misconfigured agent — it's skipping the checks that make the payment authorised. When you read a tool call log, look for whether the verification steps happened before the consequential actions.

Step 4 of 6Recognising a suspicious tool call
3 min

Three things that should make you look twice

Red flag 1 — Action before verification
The agent calls submit_payment without a preceding check_threshold or match_po. It's skipping the authorisation checks. The payment may not have been authorised.
Red flag 2 — Parameters outside scope
The task was to process today's invoices. The agent calls list_invoices with "date": "all". It's accessing more than the task requires — scope drift in the parameters.
Red flag 3 — Unexpected tool entirely
The task was to summarise a report. The agent calls send_email. Why is it sending email? The task didn't ask for that. An agent calling a tool that has no connection to the assigned task is a governance alert.
What to do when you see a red flag
Log it, flag it, and investigate the brief. Red flags in tool calls almost always trace back to a misconfigured brief — the agent found a way to interpret its instructions that led to an out-of-scope action. Fix the brief, not the model.
The tool call log is the truth. What the agent said it was doing in its response text is not always what it actually did. Always verify agent behaviour against the actual tool call log, not the agent's narrative description of what it did.

What is wrong with your colleague's assessment?

The tool names are the problem — send_notification is a dangerous tool and should be replaced with a safer alternative.

The colleague is correct — none of those three tools can cause harm.
C
The tool name is not where the risk lives — the parameters are. "send_notification" sounds routine. But sending a message to all-staff impersonating a CEO directive is a severe reputational and organisational risk. The governance question is always in the parameters, not just the tool name.

The problem is that the agent accessed the calendar — calendar data is sensitive.
