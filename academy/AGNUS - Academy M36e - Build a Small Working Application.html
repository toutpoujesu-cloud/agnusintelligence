What you will build

A small, governed approval workflow application: a system where users can submit expense claims, and an AI agent assists with categorisation and policy checking before the claim goes to a human approver. The system must have role-based access, an audit log, a scoped agent interface, and an approval gate in the logic layer.

You will direct AI to build this system in four phases: specification → scaffold → architecture review → business logic. At each phase gate, you check that governance requirements are met before proceeding.

Step 2 of 6The four build phases and their gates
4 min
Phase 1
Architecture specification
Write the complete architecture specification before directing AI to write any code. Include: data model, API surface, roles and permissions, agent integration points, approval gates, and configuration items.
Brief to AI: "Do not write any code yet. Review this architecture specification and identify any gaps or conflicts before proceeding."
Gate 1: AI has confirmed the specification is internally consistent. No build starts until Gate 1 passes.
Phase 2
Scaffold
Direct AI to build the scaffold only: database schema, API routes (no logic), auth setup, config files, approval gate stubs. No business logic.
Brief to AI: "Build the scaffold per the specification. Create the database schema, API route stubs, config file, and approval gate stub function. Do not implement business logic yet."
Gate 2: Architecture review passes all six categories from M36d. Personal data separated, audit log append-only, agent endpoints scoped, approval gate in logic layer, all thresholds in config.
Phase 3
Business logic
Direct AI to implement each component's logic: form submission, expense policy check, agent categorisation, approval workflow. One component at a time — not all at once.
Brief to AI: "Implement the expense claim submission logic. The claim must be validated against the expense policy in config, stored with a pending status, and an audit log entry created for the submission action."
Gate 3: Each component passes a unit review — does the logic match the specification? Does it enforce the access controls and governance rules?
Phase 4
Integration and test
Run the full workflow end-to-end. Submit a claim, watch the agent categorise it, trigger the approval gate, approve it, verify the audit log. Confirm all governance controls are active.
Brief to AI: "Write tests for: (1) unauthenticated user cannot access any endpoint, (2) agent endpoint returns no personal data, (3) claim above threshold triggers RequiresApprovalError, (4) audit log entry is created for every state change."
Gate 4: All four governance tests pass. Application is ready for deployment review.

Step 4 of 6Build reflection
4 min

What the build teaches

Every operator who directs AI to build governed systems will encounter the same friction points. Understanding them in advance reduces build time and improves outcome quality.

Friction point 1 — AI resists stopping at the scaffold
AI agents tend to continue past the scaffold into business logic unless explicitly told "scaffold only — stop here." The "stop here" instruction is essential. Without it, governance hooks will be embedded in business logic rather than in the structure, making them harder to review and maintain.
Friction point 2 — AI defaults to admin credentials
Without explicit role-based access control instructions, AI will often create a single superuser or use admin-level credentials for all operations. Every role must be explicitly specified in the brief.
Friction point 3 — AI puts governance values in code
Thresholds, email addresses, and limits will be hardcoded unless you explicitly specify "in config.py." The brief must include the config file specification with all governance values listed.
Friction point 4 — Agent endpoints return too much
AI will return full records unless you specify the exact fields. The agent endpoint brief must name the specific fields: "returns: claim_id, amount, description" — not "returns claim data."

Step 5 of 6Practice
3 min

A developer directs AI to build a governed HR application. Phase 1 (specification review) and Phase 2 (scaffold) complete successfully with all Gate 2 checks passing. In Phase 3, the developer directs AI to "implement all the business logic." The AI writes the full application in one pass. A review finds that the approval gate function no longer raises an error — it returns a warning instead, allowing the API to continue without approval. The approval gate stub from Phase 2 was overwritten.

What build discipline failure occurred, and what should Phase 3 briefing have said?
A
The AI made an error — the developer should have used a different AI tool for Phase 3.
B
"Implement all the business logic" in one pass allowed the AI to overwrite the stub. Phase 3 should be component-by-component: "Implement the claim submission logic — do not modify the approval gate function." Each component brief should explicitly name the functions that must not be modified. One-component-at-a-time briefing prevents AI from reorganising or overwriting governance structures built in Phase 2.
C
The Gate 2 review should have caught this — the approval gate was present after Phase 2 but changed in Phase 3.

Step 6 of 6Pass — hidden test
3 min

A team completes Gate 4 (governance tests pass) and prepares to deploy. A colleague asks: "How do we know the governance tests are actually testing the right things?" The developer responds: "They test the four things that matter most — unauthenticated access, agent data scope, approval gate enforcement, and audit logging. If these four pass, the governance structure is working." The colleague says: "But we should also test what happens when a manager tries to approve a claim above their threshold."

Who is right, and what does this illustrate about test coverage?
A
The developer is right — four governance tests covering the main failure modes is sufficient.
B
The colleague is right. The four base tests check that governance structures exist. The colleague's test checks that they work correctly for a real scenario — a manager trying to exceed their authority. A governance structure that raises RequiresDirectorApproval for an anonymous call but passes for a manager call is broken in the scenario that most commonly causes governance failures. Good governance test coverage includes both structural tests (does the gate exist?) and scenario tests (does the gate work in the actual failure scenario?).
C
Both are right — the four tests are sufficient for launch, and the scenario test can be added later.
