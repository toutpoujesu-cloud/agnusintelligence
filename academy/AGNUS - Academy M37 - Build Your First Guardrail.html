A guardrail is a constraint
that runs before the action.

An approval gate (M18) is a pause for human judgment. A guardrail is different — it is an automated check that runs before an action executes and either allows, modifies, or blocks it without human intervention. Guardrails are the automated governance layer that operates at speed.

6 steps ~18 min (includes builder) Prerequisite: M36e

Guardrail vs. approval gate

An approval gate pauses the agent and waits for a human to decide. A guardrail makes its own decision — automatically — based on pre-defined rules. It runs in milliseconds, not minutes. This makes guardrails suitable for high-volume automated processes where human approval would create unacceptable latency.

The tradeoff: guardrails cannot exercise judgment. They apply rules. If the rules are wrong, or the situation is novel, the guardrail may block legitimate actions or allow harmful ones. Guardrails and approval gates serve different purposes — and both are needed in a governed agent system.

Step 2 of 6Four types of guardrail
4 min
Type 1
Input guardrail
Runs before the agent processes input. Checks that the input is within scope, doesn't contain prohibited content, and meets format requirements. Blocks malformed or out-of-scope inputs before they reach the agent.
Example: block invoice submissions above €10,000 before the agent reads them — these require a separate manual process.
Type 2
Output guardrail
Runs before the agent's output is used or displayed. Checks that the output meets quality, accuracy, and safety criteria. Can modify output (e.g. remove personal data) or block it entirely.
Example: scan agent-generated customer responses for liability language before sending — flag any sentence containing "fault", "responsible", "liable".
Type 3
Action guardrail
Runs before the agent executes a consequential action (payment, email, record modification). Checks the action against policy rules. Can block or modify the action without needing human approval for every instance.
Example: check that a payment submission is to a pre-approved payee list — block submissions to new payees for automated approval until the payee is verified.
Type 4
Scope guardrail
Runs continuously during task execution. Monitors whether the agent's tool calls are within the configured scope. Blocks any tool call that references data or systems outside the authorised scope.
Example: block any file read outside /invoices/today/ — regardless of what reasoning the agent used to justify it.

Step 3 of 6Guardrail anatomy — three components
3 min

Every guardrail has three components

Component 1 — The check
The specific condition being evaluated. Must be deterministic — the same input always produces the same result. The check cannot exercise judgment or apply context — it applies the rule as written.
Component 2 — The action
What happens when the check fails. Three options: BLOCK (stop the operation entirely), MODIFY (change the input/output to comply), or ESCALATE (flag for human review but don't block immediately). The action must be defined — a guardrail without an action is just a monitor.
Component 3 — The log
Every guardrail trigger — pass or fail — must be logged. Without logging, you cannot audit whether guardrails are working, tune false positive rates, or demonstrate governance compliance.

Step 5 of 6Practice
3 min

A team implements a scope guardrail that blocks any file read outside /invoices/today/. After deployment, they find the guardrail is blocking 12% of legitimate invoice reads — turns out some invoices are stored in /invoices/corrections/ for amended invoices. The team debates: (A) remove the guardrail because it has too many false positives, or (B) update the guardrail to allow /invoices/today/ and /invoices/corrections/.

Which response is correct, and what does a 12% false positive rate indicate?
A
Option A — 12% false positives is too high and the guardrail should be removed or disabled.
B
Option B — update the scope to include /invoices/corrections/. A 12% false positive rate indicates the scope definition was incomplete (it didn't account for the corrections folder), not that the guardrail concept is wrong. False positives are a calibration signal — they tell you the guardrail's scope needs refinement, not that the guardrail should be removed. The correct response to false positives is to refine the check, not remove the guardrail.
C
Neither — the guardrail should be changed from BLOCK to ESCALATE to reduce friction while the scope is refined.

Step 6 of 6Pass — hidden test
3 min

A team has an output guardrail that flags responses containing phrases like "our fault" and "we are responsible." The guardrail logs show it fires on 0.3% of responses and all are correctly blocked. A manager says: "The guardrail is working perfectly — we should remove the log requirement since it's just adding overhead." A governance lead disagrees.

Who is right, and why does logging matter for a guardrail that appears to be working?
A
The manager is right — if the guardrail is working correctly, logs are unnecessary overhead.
B
The governance lead is right. Guardrail logs serve three functions: (1) Audit evidence — proving the guardrail was active and firing during any period under review. (2) Calibration data — the 0.3% rate tells you whether the guardrail is over- or under-firing over time; without logs, drift is invisible. (3) Incident investigation — if a liability phrase is ever sent, the log confirms whether it bypassed the guardrail or the guardrail failed to detect it. A guardrail without logs is ungoverned automation — you cannot prove it worked or diagnose it when it doesn't.
C
Both have valid points — reduce logging to summary statistics rather than per-event records.
