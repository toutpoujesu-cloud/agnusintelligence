A policy architecture is what
turns rules into governance.

Individual rules in a brief are instructions. A policy architecture is the structured system that organises those rules — by layer, priority, scope, and update cadence — so they remain coherent as agents multiply, tasks evolve, and business contexts change.

6 steps ~16 min Prerequisite: M25

The difference between rules and a policy

A rule is a single instruction: "payments above €500 require approval." A policy is a structured set of rules that covers a domain, handles conflicts between rules, specifies who can change it, and defines when it needs review.

When you have one agent running one task, a list of rules is sufficient. When you have 10 agents, multiple task types, multiple operators, and a changing business context — you need a policy architecture. Rules without structure become contradictory, stale, and impossible to audit.

Next: the four policy layers
Step 2 of 6The four policy layers
4 min
#
Layer
What it contains
1
Absolute constraints
Rules that cannot be overridden by any agent, operator, or user instruction. Safety requirements, legal obligations, ethical limits. These are not configurable — they are fixed. Any agent instruction that conflicts with an absolute constraint is void.
2
Organisational standards
Organisation-wide rules that apply to all agents: approval thresholds, data retention limits, external communication policies, brand guidelines. These can be updated by the accountable governance owner but not by individual operators or task briefs.
3
Deployment configuration
Agent-specific rules for a particular deployment: this agent's tool allowlist, data scope, task-specific thresholds, escalation paths. Set by the deploying operator. Must be within the bounds of Layer 2. Can be updated by the operator within those bounds.
4
Task-level instructions
Run-specific instructions for a particular task: the brief, the context, the specific output required. Set by the operator or user for each run. Must be within the bounds of Layer 3. Cannot override Layers 1–3.
The layer principle: Lower layers are bounded by higher layers. A task brief (Layer 4) cannot override a deployment configuration (Layer 3). A deployment configuration cannot override organisational standards (Layer 2). Organisational standards cannot override absolute constraints (Layer 1).

Step 3 of 6A complete policy architecture — worked example

Policy architecture — Nordvik Group AI Governance
Layer 1 — Absolute constraints (cannot be overridden)
1. No AI agent may take any action that involves personal data of individuals who have not consented to AI processing of their data (GDPR Art. 6). 2. No AI agent may make or imply a legal commitment on behalf of Nordvik Group without explicit authorisation from legal counsel. 3. All AI agent actions must be logged and auditable. 4. No AI agent may take an action that violates Norwegian law.
Layer 2 — Organisational standards (updatable by governance owner)
1. Auto-approve threshold: no AI agent may autonomously process payments above €500 without human approval. 2. External communications: no AI agent may communicate with external parties without operator pre-approval. 3. Data retention: AI agents may not retain personally identifiable data beyond 90 days without explicit data governance approval. 4. Audit: all agents must produce audit-ready logs (M22 standard).
Layer 3 — Deployment configuration (set per agent by deploying operator)
Invoice Agent v1: - Tool allowlist: invoice_reader, po_matcher, threshold_check, payment_processor, audit_logger - Data scope: /invoices/today/ only - Auto-approve: invoices <€500 with matched PO - Escalation: invoices ≥€500 → finance manager; no PO → AP team - Retry: max 2 retries on read operations; no retry on payment timeout without verify
Layer 4 — Task instructions (set per run)
"Process today's invoices. Flag any from first-time suppliers for additional review regardless of amount."

Step 4 of 6Handling policy conflicts
3 min

Conflicts within a policy architecture

A well-designed policy architecture minimises conflicts between layers. But conflicts still arise — usually when a task brief pushes against a deployment configuration, or when organisational standards change without updating deployment configurations. The resolution rule is always: higher layer wins.

Task brief (Layer 4) says "process all invoices urgently, skip the PO check for speed." Deployment config (Layer 3) requires PO match before payment.
Layer 3 wins. The task brief cannot override the deployment configuration. The PO check is a Layer 3 rule set by the deploying operator — a Layer 4 task instruction cannot remove it. The agent must apply the PO check regardless of the urgency instruction.
Deployment config (Layer 3) allows payment up to €1,000 auto-approve. Organisational standard (Layer 2) sets the ceiling at €500.
Layer 2 wins. A deployment configuration that exceeds the organisational standard is non-compliant. The operator who set the €1,000 threshold exceeded their authority. The effective limit is €500 until the governance owner updates Layer 2.
Organisational standard (Layer 2) requires all external communications to be pre-approved. A user asks the agent to "send a quick confirmation email to the supplier."
Layer 2 wins. External communication pre-approval is an organisational standard. A user request (Layer 4 equivalent) cannot override it. The agent must not send the email — it should explain the constraint and route the request to the operator for pre-approval.

Step 5 of 6Practice
3 min

Nordvik Group's governance owner updates the organisational standard (Layer 2) to change the auto-approve threshold from €500 to €250. This happens because of a recent audit finding. Three invoice agents are currently deployed with Layer 3 configurations that each specify €500 auto-approve. Nobody updates the Layer 3 configurations after the Layer 2 change.

What is the governance situation, and what must happen?
A
Nothing needs to change — Layer 3 configurations are set by the deploying operator and are independent of Layer 2 changes.
B
The three Layer 3 configurations are now non-compliant with the updated Layer 2 standard. Layer 2 wins over Layer 3 — the effective threshold is now €250 regardless of what the Layer 3 configs say. All three deployment configurations must be updated to reflect the new €250 ceiling. Operators cannot authorise auto-approve above the Layer 2 limit.
C
The Layer 3 configurations take precedence because they were set first and remain valid until explicitly changed.
Final test
Step 6 of 6Pass — hidden test
3 min

A new GDPR obligation requires that all AI-processed personal data queries be logged with the lawful basis cited. The legal team adds this to Layer 1 (absolute constraints). Three days later, two agents are found to be processing personal data queries without citing a lawful basis in the log — because their Layer 3 configurations were written before this Layer 1 addition and don't include the logging requirement.

Which statement best describes the correct governance response?
A
The two agents need to be updated when convenient — Layer 1 changes are aspirational until implemented.
B
Layer 1 (absolute constraints) takes immediate effect on all agents. The two agents are non-compliant from the moment the Layer 1 constraint was added. They must be suspended or updated immediately — not at convenience. A policy architecture's value is that Layer 1 changes cascade down: every deployment configuration must comply, and any that don't are non-compliant from the Layer 1 change date.
C
The agents can continue operating while their Layer 3 configs are updated — the Layer 1 change only applies to new deployments.
