Scaffold first. Build second.
Govern before you ship.

Scaffolding is the act of creating the application structure — directory layout, configuration files, database schema, API endpoints — before writing any business logic. It is where architecture decisions become code. Directing AI to scaffold correctly determines whether the build has governance built in from the start.

6 steps ~15 min Prerequisite: M36b

What scaffolding is

Scaffolding produces the skeleton of an application: the file structure, the database schema, the API route definitions, the configuration templates, the authentication setup. No business logic yet — just the structure everything else will be built into.

Done correctly, scaffolding encodes governance decisions into the codebase: access controls, data separation, audit hooks, and approval gate stubs. Done incorrectly, it creates a structure that works but has no governance — and adding governance later is expensive.

Next: the six-step scaffold sequence
Step 2 of 6The six-step scaffold sequence
4 min
1
Define the data model
Name every entity, its fields, and its data type. Specify which fields contain personal data, which are audit-critical, and which have retention requirements. This becomes the database schema.
Brief example: "Create a PostgreSQL schema with these tables: invoices (id, supplier_id, amount, status, created_at, approved_by, approved_at), audit_log (id, action, actor, timestamp, payload — append-only, no updates or deletes), supplier_contacts (id, name, email — personal data, separate table, 3-year retention)."
2
Define the API surface
Name every endpoint, its method, what it accepts, what it returns, and who can call it. The API surface determines what the UI and agents can do.
Brief example: "Create these API endpoints: POST /invoices (finance team only), GET /invoices?status=pending (finance team and AP team), POST /invoices/{id}/approve (finance manager only), GET /invoices/{id}/audit-log (finance director only)."
3
Define roles and permissions
Name every role, what each role can read, write, and execute. This becomes the access control configuration that every API endpoint enforces.
Brief example: "Roles: ap_team (read invoices, create invoices), finance_manager (read + approve invoices up to €5,000), finance_director (read all, approve all, read audit log). All roles require authentication."
4
Create agent integration stubs
Stub out the agent's data access interface — the specific API endpoints the agent will call, returning the exact data structure the agent expects. No agent logic yet; just the interface.
Brief example: "Create agent API stubs: GET /agent/invoices/pending (returns list of pending invoices for the agent to process), POST /agent/invoices/{id}/recommendation (agent posts its analysis — not final, awaits human approval)."
5
Create approval gate stubs
Stub out the approval gate logic in the logic layer — placeholder functions that will eventually enforce the approval workflow. No logic yet, but the structure is in place.
Brief example: "Create approval gate function: approve_invoice(invoice_id, approver_id) — checks approver role and amount threshold, raises RequiresApprovalError if threshold exceeded. Currently returns stub — will be implemented in M36e."
6
Verify governance structure before proceeding
Before any business logic is written, review the scaffold: are access controls present? Is personal data separated? Is the audit log append-only? Are agent access points scoped? Are approval gate stubs present?
Brief example: "Before proceeding to business logic: confirm all API endpoints enforce role-based access, confirm audit_log table has no DELETE or UPDATE permissions, confirm agent endpoints return only the minimum required fields."
Next: good vs. bad scaffold briefs
Step 3 of 6Good vs. poor scaffold briefs
3 min
Poor scaffold brief
"Build me an invoice processing app with a database and an API. The app should let users submit invoices, view pending invoices, and approve them. Add an AI agent that processes invoices automatically."
What the AI builds: a working application with no role-based access, personal data mixed with operational data, no audit log, agent with direct database access, approval logic in the UI.
Complete scaffold brief
"Create the application scaffold with: (1) PostgreSQL schema separating operational data, audit log (append-only), and personal data. (2) API endpoints with role-based access for ap_team, finance_manager, finance_director. (3) Agent API stubs that return only the minimum required fields. (4) Approval gate stubs in the logic layer. (5) No business logic yet — scaffold only."
What the AI builds: a governed structure with access controls, data separation, audit hooks, and governance stubs in place before any business logic is written.
The key instruction: "No business logic yet — scaffold only." Without this, AI agents combine scaffolding with business logic in one pass, which makes governance hooks hard to add retroactively.
Next: reviewing a scaffold output
Step 4 of 6Reviewing scaffold output
3 min

Five things to check in every scaffold output

Check 1 — Every endpoint has authentication
No endpoint should be accessible without authentication. Look for middleware or decorator patterns that enforce authentication before any endpoint logic runs.
Check 2 — Audit log is append-only
The audit log table should have no UPDATE or DELETE permissions. Check database migration files for constraints.
Check 3 — Personal data is separated
Personal data fields (names, emails, contact details) should be in a separate table, not mixed into operational tables. Check the database schema.
Check 4 — Agent endpoints are scoped
Agent-specific endpoints should return only the fields the agent needs. No endpoint should return entire records including personal data when the agent only needs operational fields.
Check 5 — Approval gate stubs exist in the logic layer
There should be placeholder functions in the logic layer for every approval gate defined in the architecture specification. These will be implemented later but must be structurally present now.

A developer reviews a scaffold produced by an AI agent. The database schema has one table: "applications" with fields: id, candidate_name, candidate_email, cv_text, score, status, created_at. The API has one endpoint: GET /applications (returns all records). No authentication middleware is present. No audit log table exists.

Which three scaffold checks has this output failed?
A
Check 1 (authentication) and Check 5 (approval gate stubs).
B
Check 1 (no authentication on any endpoint), Check 2 (no audit log table), and Check 3 (personal data — candidate_name and candidate_email — mixed into the operational applications table instead of a separate personal data table). All three must be fixed before any business logic is built on this scaffold.
C
Check 2 (no audit log) and Check 4 (agent endpoints not scoped).
Final test
Step 6 of 6Pass — hidden test
3 min

A team has built and deployed a production invoice processing system without a separate audit log. Six months in, a dispute arises over whether a specific invoice was ever approved, and by whom. The audit log was implemented as a field on the invoice record ("last_updated_by") rather than an immutable event log. The record now shows the current state — not the history of who did what when. The team says: "We can add a proper audit log now."

What is the governance consequence, and what does this illustrate about when audit logging must be built?
A
Adding the audit log now will resolve the dispute — historical data can be reconstructed from backups.
B
The governance consequence is irreversible: the approval history for the past six months does not exist. An append-only audit log records every action as it happens. A "last_updated_by" field records only the current state — all intermediate states are permanently lost. Adding a proper audit log now captures future events but cannot recover past ones. This illustrates that audit logging must be in the scaffold from day one — it is not a feature to be added later.
C
The team should enable database change tracking to reconstruct the history from transaction logs.
