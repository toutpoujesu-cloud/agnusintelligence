A good instruction is really two instructions.
What to do. And what to do when that doesn't work.

Welcome to Level 3 — Direct. The agents you operate from here are more complex and more consequential. Every instruction you write must have a precondition, an action, and a fallback. An instruction without a fallback is a plan that assumes nothing will go wrong.

The gap between Level 2 and Level 3

In Level 2 you learned to operate agents — read their output, identify brief failures, catch scope drift. In Level 3 you take on a more active role: you design the instructions that govern agent behavior. That shift changes what you're responsible for.

A Level 2 operator catches failures after they happen. A Level 3 operator designs instructions that prevent them, or that constrain what the agent does when they occur. The central skill in Level 3 is instruction design — and the central insight is that every good instruction has three parts, not one.

Why fallbacks get skipped

Fallbacks get skipped because writing the normal case feels complete. "Approve invoices that match the purchase order" — that's a finished instruction, isn't it? It covers the case you were thinking about when you wrote it. The problem is that instructions written around the expected case break the moment reality diverges from it — and reality always diverges eventually.

An agent with no fallback doesn't stop when the unexpected happens. It improvises. It takes the most plausible action given the instruction it has. That improvisation is where the expensive failures live.

Level 3 · DirectLearn — The three-part instruction
5 min

Precondition → Action → Fallback

This is the shape every Level 3 instruction must take. Each part is doing specific work that the other parts cannot do.

Precondition
The checkable condition
A specific, verifiable state of the world that must be true before the action runs. Not "if appropriate" — a real condition the agent can evaluate without interpretation.
"If the invoice total is within 5% of the purchase order amount…"
→
Action
The authorized response
What the agent is authorized to do when the precondition is met. Specific and scoped — not "handle it" but the exact operation.
"…approve it automatically and mark it paid."
→
Fallback
The exception behavior
What the agent does when the precondition is NOT met. This is where most instructions fail. Vague fallbacks ("handle it," "use judgment") are not fallbacks — they're improvisation licenses.
"If the variance is greater than 5%, flag it for the finance team with the variance amount highlighted — do not approve or reject it."

The fallback quality spectrum

Not all fallbacks are equal. There is a spectrum from useless to excellent. Most fallbacks people write are in the bottom half.

Fallback text
Why it does / doesn't work
✗
Useless"Handle it appropriately."
The agent has to decide what "appropriately" means. This is not a fallback — it's a blank cheque for improvisation.
✗
Weak"Use your judgment."
Same problem. Judgment belongs to the operator at design time, not to the agent at runtime. An agent exercising judgment unsupervised is an agent about to surprise you.
△
Acceptable"Flag it for a human."
Better — it names an action and a recipient. But it doesn't specify what to flag, where to send it, or what information to include. The agent may comply technically but unhelpfully.
✓
Good"Flag it for the finance manager with the variance amount highlighted."
Names the exact action (flag), the exact recipient (finance manager), and the exact information to include (variance amount). The agent can execute this without interpretation.
✓✓
Excellent"Flag it for the finance manager via Slack #invoices, include the PO number, invoice number, and variance amount. Do not approve or reject it. Mark it as 'Pending human review' in the system."
Channel, content, and prohibition all specified. The agent has no decisions to make. This is instruction design at Level 3 standard.
Next: real examples with and without fallbacks
Level 3 · DirectSee — Instructions compared
4 min

Example 1: Meeting scheduling agent

Without a fallback

"Schedule the weekly team meeting for 10am on Tuesdays."

When two key attendees have a recurring conflict at 10am on Tuesdays, the agent either keeps failing silently, reschedules the other meeting, or picks a different time without telling anyone — depending on what it considers plausible behavior when stuck. All three outcomes are bad.

With a proper fallback

"Schedule the weekly team meeting for 10am on Tuesdays. If fewer than 4 of the 6 required attendees are available at that time, propose three alternative slots in the same week and send them to the organiser for selection — do not book an alternative slot without organiser confirmation."

The fallback names the condition (fewer than 4 available), the action (propose three slots), the recipient (organiser), and the prohibition (don't book without confirmation). The agent has everything it needs to handle the exception correctly.

Example 2: Contract review agent

Without a fallback

"Review supplier contracts and flag any unusual clauses."

The agent doesn't know what "unusual" means for your business. It flags limitation-of-liability clauses, standard indemnity language, and force majeure provisions — all normal for your supplier contracts. 60 false positives. Two days of legal time to clear them.

With a proper fallback

"Review supplier contracts for clauses not present in the standard template (attached). Flag any clause that is absent from or materially different to the template. Do not flag standard limitation-of-liability, indemnity, or force majeure clauses — these are expected. For flagged clauses, note the clause text, the page number, and specifically how it differs from the template."

The precondition (deviates from template), action (flag), and constraints (what not to flag, what to include in flags) are all present. The agent can execute precisely.

The pattern: In both examples, the instruction without a fallback produced expensive work for humans to clean up. The instruction with a fallback produced a clean, usable output. The difference isn't model quality — it's instruction quality.

Level 3 · DirectPractice — Evaluate the fallback
3 min

A scheduling agent is given this instruction: "Book the client meeting for Thursday at 2pm. If that slot isn't available, reschedule it at your discretion." The agent books it on Thursday at 2pm in the client's time zone — but the operator is in a different time zone and the meeting appears at 9am for them, which conflicts with their standing team call.

What is the core problem with the fallback in this instruction?
A
The precondition is wrong — "isn't available" is too vague a trigger.
B
There is no fallback — the instruction only covers the normal case.
C
"At your discretion" is not a fallback — it is an improvisation licence. The agent had to choose a time zone and chose without guidance. A real fallback would have specified which time zone to use and what constraints apply when rescheduling.
D
The action is wrong — the agent should have confirmed before booking.

Level 3 · DirectPass — Hidden test
3 min

You are asked to review this instruction before it goes live: "Process all customer support tickets. If the issue is a billing dispute, escalate it." A senior colleague says it's fine. You think there's a problem. What is the most significant gap?

Which element would you add to make this a Level 3 standard instruction?
A
A longer preamble explaining the company's customer service philosophy.
B
A specific fallback for "process all tickets" — the instruction has no fallback for what the agent should do when it cannot process a ticket (unclear category, missing information, technical account issue). "Escalate billing disputes" is a specific sub-rule, not a general fallback. The agent has no instruction for everything outside that narrow condition.
C
More detail about which billing disputes qualify for escalation.
D
The instruction is fine — the billing escalation rule covers the most important exception.
