Architecture is the decision
that's hardest to undo.

The technology stack, deployment model, and data architecture you choose at the start of a build become increasingly expensive to change as the project progresses. This module gives you the decision framework for making those choices correctly — before an AI agent builds something that's difficult to unwind.

6 steps ~15 min Prerequisite: M36a

The architecture decision problem

When you ask an AI agent to "build an invoice processing application," it will make architecture decisions: which database, which framework, which deployment model, how to structure the data. These choices will be internally consistent — the AI will build something that works. But "works" and "right for your context" are different.

The operator's job at Level 6 is to specify the architecture before the build, not infer it from what the AI produces. This module gives you the framework to make that specification.

Next: the three architecture decisions
Step 2 of 6Three architecture decisions that matter most
4 min
Decision 1 — Monolith vs. services
A monolith is one application that does everything. Services (microservices) are separate components that each handle one thing and communicate via APIs.
Monolith: right for early stage, small team, fast iteration. Services: right when you have different scaling needs per function, multiple teams, or regulatory separation requirements.
AI agents default to monoliths — they're easier to build in one pass. Ask explicitly if services are needed.
Decision 2 — Where data lives
Data architecture determines what is stored, where, for how long, and who can access it. This is where GDPR compliance is implemented, not added later.
Personal data: minimum retention, regional storage, access controls. Audit data: append-only, immutable. Operational data: optimised for read speed vs. write accuracy based on use.
Data architecture is almost impossible to refactor after deployment. Define it before building, not after.
Decision 3 — Sync vs. async processing
Synchronous: user waits for the result. Asynchronous: task is queued, result arrives later. Most agent workflows are async by nature — they take time.
Sync: right when the result is needed immediately and the operation is fast (<2 seconds). Async: right for agent tasks, batch processing, anything that takes significant time.
AI agents built synchronously create poor user experiences for long-running tasks. Build async from the start.

Next: instructing AI on architecture
Step 4 of 6Instructing AI on architecture choices
3 min

Architecture specification belongs in the brief — before any code is written

Architecture specification — invoice processing system

DEPLOYMENT MODEL: Single monolith application (team of 3, early stage)
LANGUAGE/FRAMEWORK: Python/FastAPI backend, PostgreSQL database
PROCESSING MODEL: Async — all agent tasks queued, user polls for status
DATA ARCHITECTURE:
  - Operational data (invoices, POs): PostgreSQL, 7-year retention
  - Audit log: append-only table, no delete, no update
  - Personal data (supplier contacts): separate table, GDPR-compliant, 3-year retention, EU region only
AGENT DATA ACCESS: Via internal API only — no direct DB access
APPROVAL GATES: Implemented in logic layer — not UI
AUTHENTICATION: Role-based, finance team and AP team have separate permission scopes
The brief determines the build. An AI given this specification will build to it. An AI given "build an invoice processing app" will make its own choices — which may be correct and may not be. Specification is how you govern the build before it starts.
Next: practice
Step 5 of 6Practice
3 min

A team is building an AI agent that processes job applications. It receives CV files, extracts structured data, applies the company's scoring criteria, and routes shortlisted candidates to the hiring manager. The agent typically takes 15–30 seconds per application. The team briefed the AI: "Build a web app where the recruiter uploads a CV and gets a score." The AI built a synchronous system — the recruiter clicks upload and waits.

Which architecture decision was wrong, and what should the specification have said?
A
The monolith vs. services decision — this should have been built as microservices.
B
The sync vs. async decision. A 15–30 second processing task should always be async — the user submits the CV, receives a job ID, and is notified when the result is ready. A synchronous implementation forces the recruiter to wait 15–30 seconds per CV with a loading state, creating a poor experience and potential timeout failures. The specification should have said: "Processing is async — submit returns a job ID, status endpoint for polling, notification on completion."
C
The data architecture — CV files need separate storage from the scoring data.
Final test
Step 6 of 6Pass — hidden test
3 min

Six months after launch, a team discovers their invoice processing system stores all data — invoices, supplier contact details, audit logs — in a single unpartitioned PostgreSQL table. A GDPR audit finds that supplier contact names and emails (personal data) are stored alongside operational invoice data with no separate retention policy or access controls. The lead developer says: "We can refactor this — it's just a schema change." The data architect says: "This is not a small change."

Who is right, and what does this illustrate about when data architecture decisions must be made?
A
The developer is right — schema migrations are routine database operations.
B
The data architect is right. Separating personal data from operational data in a live system requires: migrating existing data, updating every query that touches both tables, implementing new access controls, establishing a new retention policy for existing records (some of which may need immediate deletion), and doing all of this without disrupting live operations. This is months of work, not a schema change. Data architecture decisions must be made before building — they are structurally embedded and expensive to change post-launch.
C
Both are right — the refactor is necessary but straightforward for an experienced database engineer.
