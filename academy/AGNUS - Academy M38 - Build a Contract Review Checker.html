A contract review checker
is a guardrail for legal language.

This module applies M37 (guardrails) and M32 (legal draft approval boundaries) to build a working contract review checker — an automated tool that scans contract text against a defined clause library and flags deviations before a lawyer review.

6 steps ~20 min (includes interactive checker) Prerequisite: M37

What this builds

A contract review checker is an AI-assisted tool that receives contract text and checks it against a defined set of clauses and rules. It outputs a structured review: which required clauses are present, which are missing, which deviate from the standard template, and which require lawyer escalation. It does not give legal advice — it identifies structural and pattern-based issues for qualified review.

Contract Review Checker — Architecture Specification
SYSTEM: Contract clause review tool — flags issues for lawyer review
INPUT: Contract text (plain text or extracted from PDF/DOCX)
CLAUSE LIBRARY: Defined set of required clauses, with:
  - Clause name and category
  - Required presence (mandatory / optional)
  - Pattern matching rules (keywords, phrases to look for)
  - Risk classification (missing clause = low/medium/high risk)
CHECKS:
  1. Presence check — is this clause present?
  2. Jurisdiction check — is the governing law clause Norwegian/EEA?
  3. Liability cap check — is there a liability limitation clause?
  4. Data processing check — if personal data is mentioned, is a data processing clause present?
  5. Termination check — is a termination clause present?
OUTPUT: Structured JSON + human-readable summary per clause:
  - Status: PRESENT / MISSING / DEVIATES / REQUIRES_REVIEW
  - Finding: specific text excerpt or reason for flag
  - Risk level: LOW / MEDIUM / HIGH
GUARDRAILS:
  - Output must be labelled "PRELIMINARY REVIEW — REQUIRES LAWYER CONFIRMATION"
  - Checker never provides legal advice — only structural identification
  - Any HIGH risk finding triggers immediate escalation flag
ROLES: Legal team read only (lawyers use this as a starting point)
LOGGING: All reviews logged with: document_id, review_timestamp, findings_count, high_risk_count

Step 4 of 6How to build this with AI
3 min

The three-phase build sequence for this checker

Phase 1 — Clause library
Brief to AI: "Create a JSON clause library with these clauses: governing_law (mandatory, HIGH if missing), liability_cap (mandatory, HIGH if missing), termination (mandatory, MEDIUM if missing), data_processing (mandatory if personal data mentioned, HIGH if missing), force_majeure (optional, LOW if missing). Each clause has required keywords for pattern matching."
Phase 2 — Review engine
Brief to AI: "Build a review function that takes contract text and the clause library, runs each clause check, and returns structured findings: {clause_name, status, finding, risk_level}. The function must not return any legal opinion — only structural identification. Every output must include the disclaimer: PRELIMINARY REVIEW — REQUIRES LAWYER CONFIRMATION."
Phase 3 — Output guardrail
Brief to AI: "Add an output guardrail that: (1) confirms the disclaimer is present in every output, (2) flags any HIGH risk finding for immediate escalation to legal@company.no, (3) logs every review with timestamp and finding counts. The guardrail runs before any output is returned."

Step 5 of 6Practice
3 min

A legal team deploys the contract checker and starts using it. After a month, a lawyer notices that the checker is marking a standard force majeure clause as MISSING on 30% of contracts it reviews. She checks several of the "failed" contracts and finds the clause is present in all of them — it just uses the phrase "extraordinary circumstances" rather than "force majeure." The checker's keyword list only includes "force majeure."

What type of problem is this, and what is the correct fix?
A
The checker is broken and needs to be replaced with a more sophisticated AI model.
B
The clause library has an incomplete keyword set — it misses synonymous phrases. The fix: update the clause library to add synonyms ("extraordinary circumstances", "acts of God", "events beyond reasonable control") as additional matching patterns. This is a calibration issue, not a fundamental failure. The same pattern as a guardrail false positive: the check logic needs refinement, not replacement.
C
The contracts are non-compliant — "extraordinary circumstances" is not equivalent to a force majeure clause.

Step 6 of 6Pass — hidden test
3 min

A business development manager says: "The contract checker is great — it approved a standard NDA last week without flagging anything. Can we just use its approval as final sign-off without sending to legal?" A lawyer responds: "The checker doesn't approve anything. It identifies what's there and what's missing. Whether those findings are acceptable is a legal judgment that requires a qualified lawyer — the checker just gives the lawyer a head start."

Who is right, and what does this illustrate about the role of automated checkers?
A
The manager is right — if the checker finds no issues, the document can proceed without lawyer review.
B
The lawyer is right. The checker identifies structural patterns — clause presence, keyword matches, jurisdiction flags. It does not assess whether those patterns are sufficient, correctly worded for the specific transaction, or commercially appropriate. "No flags" means the checker found none of the issues it was configured to check for — it doesn't mean no issues exist. The automated checker reduces lawyer review time; it doesn't replace lawyer judgment.
C
Standard NDAs are low-risk enough that checker sign-off without legal review is acceptable.
