An app that "works" is not the same as an app that's tested.

You've verified your to-do app yourself in M36e — a manual check, by hand. That doesn't scale, and it doesn't catch everything. The next skill: directing an AI to build a real, repeatable testing system for what it just built.

Why this matters

This is the same verification-first principle from every other module in this Academy — now applied to your own build. An agent that says "it works" after building something has told you nothing you can independently check. A test suite is what turns that claim into evidence.

What "end-to-end" actually means.

End-to-end testing checks the full journey a real person takes through the app — not just one function in isolation.

The journey for our to-do app

Open app
→
Type a task
→
Add it
→
Mark complete
→
Refresh page
→
Task still there

End-to-end testing walks this entire chain and confirms every link holds — not just that "add" works in isolation, but that it still works correctly after every other step in the journey.

Have the agent list scenarios first — as a document.

Before any test code is written, ask the agent: "List every scenario this app needs to be tested against, including edge cases and failure cases. Write it as a document."

Example scenario list for our to-do app

HappyAdd a task, it appears in the list
HappyMark a task complete, it shows a strikethrough
HappyRefresh the page, tasks are still there
EdgeTry to add a task with an empty input — nothing should happen
EdgeAdd 50 tasks — the list should still render correctly
FailureLocal storage is full or disabled — the app should not crash

Why list first, before writing test code

Writing tests immediately tempts an agent to only test what's convenient to test. Listing scenarios first — and reviewing that list yourself — is where you catch a missing case, before any test code gives you false confidence.

Bigger apps need bigger scenario lists.

A to-do app is simple. Most real applications add accounts, and accounts bring a whole category of scenarios your list must not skip.

The account journey

Sign up
→
Verify email
→
Log in
→
Use the app
→
Log out
→
Reset password

Each of these arrows is its own set of scenarios — not one test, but several, including what happens when something goes wrong along the way.

Scenarios an account system needs

HappySign up with a valid email and password, account is created
HappyLog in with correct credentials, reach the app
HappyRequest a password reset, receive a working reset link
EdgeSign up with an email that's already registered
EdgeUpdate a password — old sessions elsewhere should be logged out
FailureLog in with the wrong password repeatedly — should lock or slow down, not stay silent
FailureReset-password link is reused after already being used once — should be rejected

The lesson generalizes

Whatever your app actually does — payments, file uploads, messaging — the same discipline applies: ask the agent to enumerate the full journey for that feature, then the happy path, the edge cases, and the failure cases within it, before any test code is written.

This scenario list becomes part of the roadmap.

Testing is not a final, separate afterthought — it's its own milestone in the same roadmap file you learned to maintain earlier in this module.

The extended roadmap

1–5. (Build milestones, already completed in M36e)
6. Generate the test scenario document (happy paths, edge cases, failure cases)
7. Build the automated tests covering every listed scenario
8. Run the tests and record real results — pass or fail — in the roadmap
9. Fix any failures, and re-run before marking this milestone complete

Remember The Protocol

Testing must still follow the Rules document from The Protocol: no result is accepted unless it's verified, documented, and — where applicable — proven with a screenshot, stored in the project's results folder. Testing doesn't get an exception to the rules you already set.

Delegate testing to a second AI.

The agent that built the app has an incentive, even unintentionally, to see its own work favorably. An independent second AI checking for errors and security issues is a genuinely stronger check.

Using a second platform for testing

Tools like Codex can be pointed at a finished codebase specifically to look for bugs, security issues, and to run end-to-end tests independently of the agent that built it. This mirrors the same delegation principle from earlier in this module: don't rely on one model for everything — use a second, independent one to check the first.
