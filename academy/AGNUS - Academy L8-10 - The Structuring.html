Step 1 of 7 — Understand4 min

The blueprint becomes a physical architecture — a file system a developer, or Claude Code, can actually build from.

Phase 1 gave the vision. Phase 2 gave the behavior and aesthetics. Now the application takes physical form: the diagram, the files and their names, the folders, and the coding languages that will be used.

Why the physical structure matters

"Research shows Claude's performance degrades with added context, and guidelines recommend CLAUDE.md under 300 lines with only project-specific content."

The blueprint cannot just be dumped into Claude as context. It must be structured into a file system that Claude can navigate efficiently. The physical structure of the project determines how well Claude can build it.

Step 2 of 7 — What a Real Structure Looks Like5 min

An example — for you to recognize, not to write

You will never type any of this by hand. This is what Claude will hand back to you. Your only job is to look at it and ask: does this actually separate the app's rules from its code? Does it look like it belongs to my project, or could it be for any project?

your-project/ ├── CLAUDE.md # Tech stack, dev commands, project conventions (~25 lines) ├── .claude/ │ ├── rules/ # Project-specific patterns only │ │ ├── api-contracts.md # Your actual endpoints │ │ └── troubleshooting.md # Symptom → Diagnosis → Fix │ ├── memory/ # Persists knowledge across sessions │ │ ├── MEMORY.md # Index (always loaded by Claude Code) │ │ └── *.md # Topic files: debugging, patterns, gotchas │ ├── commands/ # Slash commands: /review, /test, /lint │ └── settings.local.json ├── docs/ │ └── decisions/ # Architecture Decision Records └── scripts/ # Smoke tests with PASS/FAIL/WARN output
"Only include what Claude would get wrong without it." Claude already knows HTTP status codes, REST principles, and how to paginate. What Claude needs is project-specific information — your API base URL, your auth mechanism, your naming conventions, your migration commands, your specific gotchas.

Step 4 of 7 — Recognizing a Good Structure6 min

Different apps, different shapes — here's how to tell they're both real

You don't need to know what a "JPA Entity" or a "DTO" is. What matters is the pattern: real structures separate concerns into clearly-named folders instead of dumping everything into one file. If Claude gives you one giant file instead of this kind of breakdown, that's a sign to ask again.

src/main/java/com/yourproject/ ├── config/ # Configuration classes (Security, Swagger, caching) ├── controller/ # REST Controllers (API layer) ├── dto/ # Data Transfer Objects (Request/Response) ├── entity/ # JPA Entities (Database Access) ├── exception/ # Global exception handling ├── repository/ # Data access layer ├── security/ # Auth logic ├── service/ # Business logic layer └── util/ # Utility classes

A different project, a different stack — same recognizable pattern

your_project/ ├── README.md ├── CLAUDE.md # Project rules Claude reads on every session ├── requirements.txt # Python dependencies ├── .gitignore ├── .claude/ # All Claude Code configuration │ ├── settings.json # Shared permissions, hooks, model config │ ├── settings.local.json # Your personal machine overrides (gitignored) │ ├── skills/ # Reusable prompt packs │ ├── commands/ # Custom slash commands (/deploy, /review) │ └── agents/ # Sub-agents Claude can spawn └── arc/ # Application source code ├── posts.py ├── authors.py ├── comments.py ├── post_service.py ├── author_service.py └── comment_service.py
The key insight: the .claude/ folder is separate from the application code (arc/). Claude's configuration lives alongside the code, not inside it.

Step 6 of 7 — Asking for the Full Document6 min

The prompt that gets you the complete deliverable — copy this into Claude

Deliver the complete project structure as a set of files. For each file, provide: The full path and filename The purpose of the file A template or skeleton of its content Any placeholders that need to be filled in Also provide: The language choices and reasoning The framework choices and reasoning The database choices and reasoning The deployment platform choices and reasoning

Backend and frontend are usually two separate structures — another thing to check for

app/ ├── controllers/ │ └── application_controller.rb ├── models/ │ ├── todo.rb │ └── category.rb ├── serializers/ │ ├── todo_serializer.rb │ └── category_serializer.rb ├── db/ │ ├── migrate/ │ └── schema.rb └── config.ru -- frontend -- my-app-frontend/ ├── src/ │ ├── components/ │ ├── App.js │ └── index.js └── package.json

Ask for the reasoning too, in writing — Architecture Decision Records

docs/ └── decisions/ ├── 001-use-fastapi.md ├── 002-use-postgres.md └── 003-use-redis-caching.md

ADRs capture significant design decisions, making the reasoning behind the structure explicit and persistent.

Step 7 of 7 — Judging the Result7 min

One file matters more than the rest: CLAUDE.md — and you can judge it without knowing code

CLAUDE.md is the note Claude Code will read every single time it works on your project later. You don't need to write it — Claude does. But you need to know what "good" looks like, so you can tell Claude to fix it if it isn't: short (under ~300 lines) and specific to YOUR project, never generic.

SectionWhat it includesWhy
Project OverviewName, description, purposeContext
Tech StackLanguage, frameworks, databasesWhat to use
Dev CommandsInstall, test, run, lintHow to work
ConventionsNaming, formatting, patternsConsistency
Project-Specific GotchasCommon pitfalls, fixesEfficiency
Should NOT be in CLAUDE.md
  • HTTP status code tables — Claude knows REST
  • Pydantic/Zod examples — Claude knows these libraries
  • Generic security advice — Claude knows basics
  • Pagination patterns — Claude knows how to paginate
  • YAML templates — Claude can write from scratch
SHOULD be in CLAUDE.md
  • Your actual API base URL and auth mechanism
  • Your specific migration commands
  • Project-specific gotchas (e.g. "Cilium BPF map overflow — symptom → diagnosis → fix")
  • Your naming conventions and required labels
  • Project-specific conventions Claude can't infer from code
