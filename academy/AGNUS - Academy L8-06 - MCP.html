AGNUS Academy Level 8 · Foundation L8-06 — MCP: The Client-Server Model
Step 1 of 4 — Understand4 min

MCP is a standard plug, not a proprietary cable, for connecting an agent to outside tools and data.

Before a standard existed, every agent framework needed its own custom code to connect to every tool. The Model Context Protocol (MCP) defines one shared way for an agent (the client) to talk to any tool or data source (a server) that speaks the same protocol.

Why this matters

Without a shared standard, connecting an agent to ten different tools means writing ten different custom integrations, and every tool update risks breaking one of them. MCP exists specifically to remove that duplicated, fragile integration work.

Step 2 of 4 — See5 min

Client and server, and what flows between them

MCP Client

The agent (or the framework running it). Requests data or asks a tool to be run.

⇄
MCP Server

A tool, database, or service exposing its capabilities in the shared MCP format.

Any MCP-compliant client can talk to any MCP-compliant server, regardless of who built either one — the same way any web browser (client) can talk to any website (server) because both speak HTTP.

The three primitives MCP defines — click each

Resources
Read-only data the client can pull in — a file, a database record, a document. The agent reads it, but doesn't act through it.
Tools
Actions the client can invoke — this is the M03 "tool call" concept, standardized so any MCP client can call any MCP server's tools the same way.
Prompts
Reusable, pre-written prompt templates a server can offer — a standardized way to share a well-tested instruction pattern, rather than every client reinventing it.

A company builds one MCP server exposing their internal ticketing system. Three different teams, using three different agent frameworks, are all able to connect their agents to it without any framework-specific integration code. What does this demonstrate about MCP?

AA single MCP-compliant server can be used by any MCP-compliant client, regardless of framework — exactly the shared-standard benefit MCP is designed to provide.
BThis is a coincidence, and normally each framework would still need its own custom integration.
CThis only works because all three frameworks happen to use the same underlying model.
DThis proves the ticketing system is a Resource, not a Tool.
