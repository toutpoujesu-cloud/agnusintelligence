Why you need to understand application structure

An AI agent given "build me an app to process invoices" will build something. It may build it well. But as the person directing it, you need to understand what it built — which part handles the logic, which part stores the data, which part the user interacts with — so you can review it, spot problems, make decisions about architecture, and govern what gets deployed.

This is not a software engineering course. It is the minimum architectural literacy needed to direct AI that builds software and to govern what it produces.

Next: the four application layers
Step 2 of 6The four application layers
4 min

Every application has four layers — even simple ones

Understanding these four layers tells you where to look for different types of problems and where governance decisions live.

UI Layer
Presentation — what the user sees and interacts with
Buttons, forms, screens, dashboards. This layer has no memory — it receives data and displays it. Logic does not live here.
Examples: web pages, mobile screens, chat interfaces, dashboards
Logic Layer
Business rules — how the application decides and acts
Validation, calculations, workflow decisions, API calls. This is where agent instructions, approval gates, and governance rules live. This layer should not communicate directly with the database — it calls data through a defined interface.
Examples: invoice approval rules, escalation logic, agent orchestration
Data Layer
Storage and retrieval — where information persists
Databases, file stores, caches. The application reads and writes here through controlled interfaces — not directly. Data governance, GDPR compliance, and retention policies live here.
Examples: invoice records, customer data, audit logs, agent configurations
Infrastructure
Runtime — where the application runs
Servers, cloud platforms, authentication, security. This layer handles who can access the system, how it scales, and what happens when things fail.
Examples: cloud hosting, API keys, authentication, monitoring, backup
Next: where agents live in the stack
Step 3 of 6Where agents live in the application stack
4 min

Agents are logic layer components — with specific integration points

An AI agent is a component of the logic layer: it receives inputs, applies rules, makes decisions, and calls tools. Understanding where agents connect to each layer determines what they can access, what they can affect, and where governance controls must be placed.

Agent ↔ UI Layer
Input and output interface
The agent receives user requests from the UI and returns results that the UI displays. The UI layer should not expose raw agent output without formatting and validation checks.
Governance: the UI should clearly label AI-generated output and not present agent suggestions as confirmed facts.
Agent ↔ Logic Layer
Peer components — orchestration and rules
Other logic components may call the agent or the agent may call them. Approval gates, escalation routers, and policy engines are logic layer components that the agent interacts with.
Governance: agent-to-agent calls should follow the M19 authority chain rules — no implicit permission inheritance.
Agent ↔ Data Layer
Read and write access — the highest-risk interface
Agent data access must be through controlled interfaces — not direct database access. The data scope constraint from M17 is implemented here. The agent requests data through an API; the API enforces access controls.
Governance: agents must never have direct database credentials. Data access is through a scoped API that enforces M17 constraints.
Agent ↔ Infrastructure
Authentication and resource limits
Agents run as authenticated service accounts with defined resource limits. API keys, rate limits, and timeout configurations live here. An agent with no resource limits can consume unbounded compute.
Governance: agents run as least-privilege service accounts. No agent should have admin credentials to any system.

Step 4 of 6A request flowing through the stack
3 min
Request flow — "Show me all invoices above €500 awaiting approval"
1
UI
User clicks "Pending Approvals" filter. UI sends request to the logic layer: GET /invoices?status=pending&min_amount=500
2
Logic
Invoice service validates the request, confirms the user has approval authority, queries the data layer through a defined interface: SELECT invoices WHERE status='pending' AND amount>500 AND approver_id=user.id
3
Data
Database returns the matching records. The data layer enforces that the query only returns records the user is authorised to see — even if the logic layer requested more.
4
Logic
Invoice service formats the response, applies any business rules (e.g. flags invoices within 24 hours of expiry), and returns structured data to the UI.
5
UI
UI renders the invoice list with pending status badges and expiry warnings. The user sees the result.
Agent role
Logic
If an AI agent is used to summarise the pending invoices or flag anomalies, it receives the structured data from the logic layer — not raw database access. Its output goes back to the logic layer for validation before reaching the UI.
The governance principle: Every agent operates on data that has already been filtered and authorised by the layers above and below it. The agent never determines what data it can see — the data layer and logic layer access controls determine that. The agent works within the envelope, not on the envelope.

Step 5 of 6Practice
3 min

A developer proposes this architecture for an AI-assisted recruitment application: "The AI agent will have direct read access to the HR database so it can query candidate profiles when needed. This is faster than going through an API." The architect objects: "The agent should access candidate data through the HR API, not directly."

Why is the architect right?
A
APIs are always faster than direct database access — the performance argument is wrong.
B
Direct database access bypasses all access controls. The agent would be able to query any candidate data in the database — not just the authorised subset for the current task. The HR API enforces who can see what data, applies GDPR minimisation (returning only the fields relevant to the recruitment stage), and logs every access. Direct DB access removes all of these governance layers and violates data minimisation.
C
The API provides caching that makes it faster and simpler for the agent to use.
Final test
Step 6 of 6Pass — hidden test
3 min

A product manager reviews an AI agent's architecture diagram and notices the agent's approval gate logic is implemented in the UI layer — it shows an "approve" button to users after the agent produces a suggestion, and the approval is recorded in the UI state. The architect says: "Approval gate logic should be in the logic layer, not the UI layer."

Why does it matter which layer the approval gate lives in?
A
It doesn't matter for governance — the approval still happens before the action proceeds.
B
UI-layer approval gates can be bypassed by anyone who can make direct API calls to the logic layer — the button not being clicked doesn't stop the action if the logic layer doesn't enforce the gate. Logic-layer approval gates cannot be bypassed by UI manipulation: the action will not proceed until the logic layer receives the confirmed approval signal. For governance, the gate must be in the logic layer where it is enforced at the code level, not in the UI where it is enforced at the display level.
C
The UI layer is fine for approval gates — it's simpler to implement there and produces the same result.
