Escalation Design

An agent that doesn't know when to stop is more dangerous than one that stops too often. Escalation design is how you give agents the judgment they cannot have on their own — by building the decision into the system before it is needed.

6 steps~12 minPrerequisite: M25
Step 1 of 6Why agents need escalation paths

In M25 you learned what intervention controls are — the tools that allow humans to pause, override, or stop agents. In M26 you learn the design question that comes before intervention: how does the agent know it has reached a point where human input is needed?

A well-designed agent does not wait to be stopped. It knows — based on defined rules built into its governance architecture — when it has encountered a situation outside its scope, above its authority threshold, or ambiguous enough to require human review. Escalation design is the work of defining those rules before the agent is deployed.

The failure mode is common: agents that are given goals without escalation rules optimise toward the goal until something goes wrong. By then, the harm may already have occurred. Escalation design moves the judgment from runtime to design time — which is the only moment it can be made carefully.

The escalation principle: Every agent task should have a defined answer to three questions — what situations require human input, who receives the escalation, and what happens to the task while the human reviews. These are governance decisions, not technical defaults.
Next: the three escalation levels
Step 2 of 6The three escalation levels
Level 1 — Notify
Inform without stopping
The agent proceeds but notifies a human. Used for actions that are within scope but above a defined significance threshold. The notification creates a record and gives the human an opportunity to intervene — but does not require it. Appropriate for: high-value actions that are pre-approved by type but warrant visibility; anomaly detection that doesn't reach a stop threshold.
Level 2 — Pause
Stop and request approval
The agent pauses, queues the action, and waits for human approval before proceeding. Used for actions above the agent's autonomous authority threshold or in situations outside its defined scope. The task is not abandoned — it is held. Appropriate for: actions above financial or authority thresholds; novel situations the agent has not handled before; actions with significant external consequences.
Level 3 — Stop
Halt and report
The agent stops the task entirely, does not queue for later execution, and reports to a human with full context. Used when continuing would risk harm regardless of approval, or when the agent has detected a situation that suggests the task itself was misspecified. Appropriate for: potential policy violations; detected adversarial conditions; tasks that cannot safely wait for approval.
Step 3 of 6Escalation triggers

An escalation trigger is the specific condition that causes an agent to move to Level 1, 2, or 3. Triggers must be defined before deployment — they cannot be left for the agent to determine at runtime, because an agent reasoning about whether to escalate has a conflict of interest with its assigned goal.

Trigger typeExampleEscalation level
Value thresholdInvoice amount exceeds €5,000Level 2 — Pause

Novelty triggerSituation not covered by any defined ruleLevel 2 — Pause

Risk indicatorPotential policy violation detectedLevel 3 — Stop
External signalThird-party system returns error or unexpected stateLevel 1 or 2
Repetition limitAgent has retried the same step N times without successLevel 3 — Stop
The repetition limit is the most commonly missed trigger. An agent that retries indefinitely is an agent that cannot recognise failure — which is itself a failure mode that requires human input.
Step 4 of 6Who receives the escalation

The escalation recipient is as important as the escalation trigger. An escalation that goes to the wrong person — or to no one — is not an escalation. It is a log entry that no one will read in time to make a difference.

Escalation routing must be defined explicitly for each trigger type. The routing decision answers four questions: Who has the authority to approve this action? Who has the expertise to assess this situation? Who is reachable within the required response window? Who is the fallback if the primary recipient is unavailable?

The response window problem is where escalation design most often fails in practice. A Level 2 escalation that requires human approval before the agent proceeds is only useful if the human can respond within the task's operational timeline. An invoice-processing agent that escalates to the finance director at 11pm on a Friday, with a 2-hour response window before the task expires, has an escalation design that doesn't work.

Response window requirements should be part of the escalation design — and the design should include what happens if the window expires without a response. The three options are: default to rejection (safest), default to approval (only for very low-risk actions), or extend the window and notify again.

Good practice: Define the response window, the default on timeout, and the fallback recipient for every escalation type. Document this in the agent's governance specification — not just the system prompt.
Step 5 of 6Practice

An accounts-payable agent is configured with the following rules: invoices under €500 with a matching purchase order may be approved automatically; invoices €500–€5,000 require finance manager notification; invoices above €5,000 require finance director approval. A €4,200 invoice arrives with a matching PO. The finance manager is on annual leave. The system has no fallback recipient configured.

What happens — and what should have been designed differently?
A
The agent should approve the invoice automatically because the PO matches, even though the amount triggers the notification rule. Matching PO is the primary control.
B
The escalation fails because there is no fallback recipient. The agent should pause the invoice (Level 2) and hold it unprocessed. The design gap is the missing fallback — the escalation specification should have defined a secondary recipient (e.g. finance director) for when the primary is unavailable, and a timeout default.
C
The agent should reject the invoice entirely (Level 3 — Stop) because it has no one to escalate to. Rejection is always the safe default when escalation fails.
Step 6 of 6Pass — hidden test

A legal document review agent has been instructed to flag any contract clause that conflicts with standard company policy. While reviewing a contract, it encounters a clause it cannot categorise — it does not conflict with any defined policy, but the agent is not confident it has understood the clause correctly. The agent has no escalation rule for "uncertain interpretation."

What should the agent do — and what governance gap does this reveal?
A
The agent should flag the clause as potentially conflicting, to be safe. Over-flagging is always better than under-flagging in legal review.
B
The agent should proceed without flagging — if there is no policy conflict it can identify, it has no basis for escalation. The absence of a conflict is the correct output.
C
The agent should escalate at Level 2 — Pause — because uncertainty about its own interpretation is a novelty trigger. The governance gap is the missing escalation rule for interpretation uncertainty. A complete escalation design must include a trigger for "agent uncertain about its own output" — not just rules for clear policy violations. Confident incorrect outputs are more dangerous than paused uncertain ones.
