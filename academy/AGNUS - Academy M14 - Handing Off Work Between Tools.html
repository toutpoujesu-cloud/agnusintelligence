Module 14 of 49 · Level 2 · Operate

The handoff is where
most pipeline errors live.

When an agent chains tools together, it passes data from one tool to the next. The quality of that handoff — what data is passed, in what format, with what validation — determines whether the chain produces a reliable result or silently propagates errors through every subsequent step.

6 steps ~14 min Prerequisite: M13

What a tool handoff is

When an agent calls tool A and uses the result as input to tool B, that is a tool handoff. In complex agent tasks, there can be 10, 20, or 50 of these handoffs in a single run. At each handoff point, the agent makes a decision: what from the previous result do I carry forward, and in what form?

Errors at handoff points compound. An error introduced at step 2 in a 10-step chain is carried forward into steps 3, 4, 5... through to step 10. The final output is wrong, but tracing the error back to step 2 requires reading the full chain.

A clean handoff: Each step carries forward only what the next step needs, verifies that data is in the expected format, and confirms that the input to the next step was derived correctly from the previous result.
Next: how handoffs fail
Step 3 of 6How handoffs fail
4 min
Failure 1 — Type mismatch
Tool 1 returns amount as string: "320"
Tool 2 expects amount as number: 320
Tool 2 receives "320" and either fails or processes it as text
The handoff passed a string where a number was expected.
Prevention: include explicit type validation at handoff points. If the brief specifies "pass the amount to submit_payment," also specify "ensure it is passed as a number, not a string."
Failure 2 — Wrong field extracted
Tool 1 returns: {invoice_total:320, shipping_cost:45}
Agent passes shipping_cost to the payment tool instead of invoice_total
€45 is paid instead of €320
The agent extracted the wrong field from the result and carried it forward.
Prevention: be explicit in the brief about which field to carry forward: "pass invoice_total to submit_payment, not shipping_cost."
Failure 3 — Null not caught
Tool 1 returns: {po_match: null}
Agent carries null forward into submit_payment(po_match:null)
Payment submitted without a confirmed PO match
Null was not validated before being carried forward. The agent treated null as a value.
Prevention: explicit null check at handoff: "if po_match is null, stop and flag. Do not proceed to payment."
Next: the four handoff rules
Step 4 of 6Four rules for clean handoffs
3 min
Rule 1
Name the field explicitly
Don't say "pass the result to the next tool." Say "pass invoice_total from the result to submit_payment." Explicit field names eliminate wrong-field extraction errors.
Rule 2
Check for null before carrying forward
Any field that must exist for the next step to be valid needs an explicit null check. "If po_match is null or false, stop." Don't assume a result is non-null.
Rule 3
Verify format at handoff
If the next tool expects a number, verify the handoff value is a number. If it expects an ISO date, verify the format. Type mismatches are silent — they don't always cause obvious errors.
Rule 4
Carry only what the next step needs
Don't carry the entire previous result forward "in case it's needed." Carry only the specific fields the next tool requires. Unnecessary data in context creates scope for the agent to use the wrong field.
Next: practice
Step 5 of 6Practice
3 min

A brief says: "Read the customer record, then send them an email confirming their order." The customer record tool returns: {customer_id:"C-441", name:"Ingrid H.", email:"ingrid.h@example.no", last_order_value:€420, overdue_balance:€180}. The agent sends the email but includes the overdue balance in the message body, which was not intended.

Which handoff rule was violated?
A
Rule 2 — the null check was missing for the email address field.
B
Rule 4 — the entire customer record was carried forward, including fields (overdue_balance) that had no place in the email. The brief should have specified exactly which fields to use: "pass customer name and email address to the email tool. Do not include financial data."
C
Rule 3 — the email address format was not verified before it was passed to the email tool.
Final test
Step 6 of 6Pass — hidden test
3 min

An agent is processing a list of 200 supplier records. Step 1 reads each record and extracts the supplier ID. Step 2 queries the PO database for the supplier's outstanding POs. Step 7 (after several intermediate steps) submits a consolidated payment for each supplier. A review shows that one payment was submitted for €0. Tracing back, step 2 for that supplier returned null (no outstanding POs) — and the null was carried forward through steps 3–6 without being caught, eventually reaching the payment tool as amount:null, which was treated as amount:0.

Which handoff rule would have prevented this, and at which step?
A
Rule 1 — the field name should have been specified more clearly at step 2.
B
Rule 2 — null check at step 2. When step 2 returned null (no outstanding POs), that was the signal to stop processing this supplier, not to carry null forward. The brief should have specified: "if the PO query returns null or empty, skip this supplier and log it — do not proceed to payment steps." Applied at step 2, this would have caught the case before it propagated through 5 further steps.
C
Rule 3 — the type of the amount should have been validated before step 7.
