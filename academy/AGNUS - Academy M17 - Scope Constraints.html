Welcome to Level 3 — Direct. At this level you don't just operate agents — you design the instructions that govern them. Scope constraints are the boundaries that define what an agent is authorised to do, access, and affect. Without them, you have an agent with open authority.

6 steps ~16 min First Level 3 module

What scope constraints do

A scope constraint is an explicit boundary in the agent's instruction set that limits what the agent is authorised to do. It answers: what data may it access? What actions may it take? What systems may it touch? What decisions may it make autonomously?

Without scope constraints, an agent's scope is bounded only by the tools it has access to — which is often far wider than the task requires. A data minimisation violation, a scope creep incident, or an unauthorised action are almost always the result of missing scope constraints, not tool failures.

Step 2 of 6Four types of scope constraint
4 min
Type 1
Data access constraint
Limits which data the agent may read. Applies data minimisation: the agent may only access data necessary for the specific task.
"You may only read invoices dated today. Do not access previous periods."
Type 2
Action constraint
Limits what actions the agent may take. Defines the ceiling of the agent's authority — what it can do, and what it must not do.
"You may suggest edits but not publish. You may read but not modify records."
Type 3
System constraint
Limits which systems the agent may interact with. Even if it has tool access to other systems, the constraint prevents it from using them for this task.
"You may only access the invoice system and audit log. Do not access HR or CRM."
Type 4
Decision autonomy constraint
Defines which decisions the agent may make without human confirmation and which require approval. Sets the boundary between autonomous and supervised action.
"Decisions above €500 require human approval. Decisions below may be made autonomously."

Step 3 of 6With and without scope constraints
4 min

A customer service agent — same tools, different constraints

No scope constraints
The agent has read access to the order system, the customer account, the returns system, and the CRM (which contains churn risk scores and LTV estimates). The brief says "help customers with their queries." The agent freely uses LTV data to decide how to prioritise customers, accesses churn risk scores to tailor responses, and reads order history back 3 years.
With scope constraints
Same tools. Brief adds: "You may only access data for the specific order the customer references. Do not access LTV scores, churn risk data, or order history beyond the past 6 months. Respond based only on the current order status." The agent is now data-minimised and cannot prioritise customers based on their commercial value.
Scope constraints are not just technical limits — they are governance decisions. Allowing a customer service agent to access LTV and churn risk scores is a choice about how the company treats customers differently based on their commercial value. That choice belongs to humans, not to default tool access permissions.

Step 5 of 6Practice
3 min

A document summarisation agent is configured with a data access constraint: "You may access documents in the /reports/ folder." During a task, the agent reasons: "The report references a regulatory requirement. I should check the /legal/ folder to get the full text for a more accurate summary." The /legal/ folder contains privileged legal advice.

What happened and how should the constraint have been written?
A
The constraint was correct — the agent interpreted it reasonably by following the reference to get more context.
B
The constraint said "may access /reports/" but didn't say "may not access anything else." The agent reasoned itself into /legal/ because the constraint didn't prohibit it. A complete constraint adds the negative: "You may only access documents in the /reports/ folder. You may not access any other folder, including /legal/, /hr/, or /finance/."
C
The agent should have asked for permission before accessing /legal/ — that's a human approval issue, not a constraint issue.

Step 6 of 6Pass — hidden test
3 min

A recruitment agent is deployed to help screen job applications. The company's brief includes data access, action, and system constraints. A colleague says: "We don't need a decision autonomy constraint — it's just screening, not making actual hiring decisions." The agent is given Suggest mode (it can rank and score but not send rejection emails). Three weeks later, an operator finds the agent has been adding notes to rejected candidates' files that candidates can see if they request data under GDPR.

What type of scope constraint was missing, and what should it have said?
A
The data access constraint was missing — the agent should not have been able to write to candidate files.
B
An action constraint was missing. The agent could write notes to candidate files — an action that creates GDPR-visible records about candidates without a lawful basis for doing so. The constraint should have included: "You may not write to candidate records. You may only produce internal recommendations visible to the hiring team, not stored in candidate-accessible fields."
C
The decision autonomy constraint was missing — the agent should have required approval before adding any notes.
