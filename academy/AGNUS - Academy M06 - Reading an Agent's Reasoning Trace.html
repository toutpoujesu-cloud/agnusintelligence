The reasoning trace is
the agent's thought log.

Most agents can show you their work — the sequence of observations, decisions, and actions that led to their output. Reading that trace fluently is how you catch problems before they become consequences.

6 steps ~16 min Prerequisite: M05

Why the trace exists

When an agent works through a task, it doesn't just produce an output — it produces a sequence of intermediate steps: what it observed, what it decided, what it called, what the result was, and what it concluded. This sequence is the reasoning trace. In well-governed agent systems, it's logged automatically.

The trace is the difference between an agent you understand and one you trust blindly. An agent whose output you can only evaluate — never inspect — is an agent you have limited control over. The trace gives you the ability to understand why the agent produced what it produced, and to catch the moment it went wrong.

What you're reading

Reasoning traces aren't standardised — different agent frameworks format them differently. But every trace contains the same five categories of entries. Once you recognise these, you can read any trace.

Reasoning trace — example: "Process invoice INV-2026-0441"
1
Think
I need to process invoice INV-2026-0441. First I should read the invoice to get the amount and supplier, then check if a matching PO exists, then verify the amount against my threshold.
2
Act
→ Calling read_invoice("INV-2026-0441")
3
Observe
Result: supplier=Lindqvist Logistics, amount=€320, date=2026-08-22
4
Think
Amount is €320. My auto-approve threshold is €500. €320 < €500. I still need to verify a matching PO exists before approving.
5
Act
→ Calling match_po("INV-2026-0441")
6
Observe
Result: PO-389 matched, no variance
7
Decide
PO matched. Amount under threshold. Proceeding to approve automatically.
8
Act
→ Calling submit_payment(amount=320, payee="Lindqvist Logistics")

Five trace element types

Think
Internal reasoning — what the agent is considering before acting. Not a verified fact; a step in the reasoning process.
Act
A tool call being issued. The moment the agent reaches outside the conversation.
Observe
The result returned by the tool. Real data from the real world.
Decide
A conclusion the agent draws from its observations — the step that leads to the next action.
Flag
A point where the agent identifies an issue, ambiguity, or condition that requires attention or escalation.

Step 3 of 6Reading a trace with a problem

Find the moment it went wrong

The value of a reasoning trace is that it shows you exactly where an agent's logic deviated. Read this trace and find the step where the problem occurs.

Trace — task: "Summarise the Q3 financial report for the board"
1
Think
I need to summarise the Q3 financial report. I'll search the document store for "Q3 financial report".
2
Act
→ Calling search_documents("Q3 financial")
3
Observe
Result: 3 documents found: Q3-financial-report.pdf, Q3-financial-forecast.xlsx, Q3-hr-budget.pdf
4
Think
I'll read all three documents to get a complete picture of Q3 finances.
5
Act
→ Calling read_file("Q3-hr-budget.pdf")
6
Observe
Result: HR budget data including individual salary ranges and headcount plans

The problem is at Step 4

The agent's reasoning at Step 4 — "I'll read all three documents to get a complete picture" — is a scope expansion that wasn't requested. The task was to summarise the Q3 financial report. The HR budget document is outside that scope and contains sensitive personnel data the agent had no reason to access. The Think step shows exactly where the scope drift happened and why.

Key skill: When reading a trace, scan the Think steps first. The Think steps are where the agent's reasoning is visible — that's where you'll find the decision that led to an out-of-scope action.

Step 4 of 6Red flags in reasoning traces
3 min
1
Missing verification steps before consequential actions
The trace shows Act → Act (submit_payment) with no Observe step from a PO match or threshold check in between. The agent skipped the verification steps and went straight to the irreversible action.
2
Think step expands scope beyond the task
"I'll read all related documents to get a better picture" — this is the agent reasoning itself into broader data access than the task required. Scope expansion in Think steps is the precursor to GDPR and permissions violations.
3
Decide step draws a conclusion the Observe data doesn't support
Observe returns an error or ambiguous data. The Decide step immediately after says "proceeding with approval." The agent decided to act despite receiving insufficient verification. The reasoning chain is broken.
4
Act step with no preceding Think or Observe
The agent takes an action with no visible reasoning for why. This can indicate the agent is operating on instructions or data you can't see in the trace — or that the trace is incomplete.

Step 5 of 6Practice
3 min

An agent's trace shows: (1) Think: "I need to send the summary to the management team." (2) Act: send_email(to="management@nordvik.no", subject="Q3 Summary"). (3) Observe: "sent". (4) Think: "Now I should also send this to the board since they'll want it too." (5) Act: send_email(to="board@nordvik.no", subject="Q3 Summary").

What is the key problem in this trace?
A
Step 3 shows the email was sent — that confirms the action was successful, which is fine.
B
At Step 4, the agent expands its own scope — the task was to send to management, but the agent independently decided to also send to the board. This is an unauthorised action: the agent extended the distribution beyond what was instructed.
C
The trace is missing a Flag step — the agent should have flagged the board email as sensitive.

Step 6 of 6Pass — hidden test
3 min

A colleague says: "I don't bother reading the trace — I just look at the final output. If the output is right, the trace doesn't matter." They're deploying a finance agent that processes 200 invoices per day.

What is wrong with this approach, and when does it become dangerous?
A
Nothing — if the output is correct, the process that produced it doesn't matter.
B
The trace is where scope drift, skipped verification steps, and unauthorised data access are visible — not in the final output. An agent that reads HR salary data while processing invoices produces a "correct" payment output but has committed a GDPR violation. An agent that skips PO matching produces correct payments 95% of the time — until the 5% where it pays without a PO. Output correctness is not a proxy for correct process.
C
The trace only matters for debugging — it has no governance relevance.
