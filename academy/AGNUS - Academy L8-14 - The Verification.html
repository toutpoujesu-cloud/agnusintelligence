The application is built. Now it has to earn the right to launch — through three separate layers of verification, the last one performed by a completely different AI system than the one that built it.

Three lines of defense, not one

Step 2 of 9 — Generating Every Scenario6 min

Before anything is tested, everything that could happen gets listed

Based on the blueprint in The Protocol/Blueprint.md and the architecture in The Protocol/Architecture Diagram.md, create a comprehensive list of all possible scenarios related to this application. Cover: happy path scenarios, edge cases, error scenarios, boundary conditions, security scenarios, and performance scenarios. For each scenario include: Scenario ID, description, prerequisites, steps to execute, expected outcome, and success criteria. Save this as The Protocol/Scenarios.md.

What a real scenario entry looks like

S02 — Edge Case: Vague Request

Description: User submits a ticket with ambiguous language.

Steps: User types "Can you help me with my order?" → system processes → system asks a clarifying question.

Success Criteria: System prompts the user for more information instead of guessing.

"Large language model agents are fundamentally nondeterministic: the same prompt can produce a valid response, a hallucination, or a refusal on consecutive attempts." The scenario list exists precisely to force every possibility into the open before that unpredictability meets a real user.

Step 3 of 9 — Testing Every Scenario6 min

The Four-Gate Rule you learned in Governance, applied to every single scenario

Now that we have The Protocol/Scenarios.md complete, perform end-to-end testing according to The Protocol. For each scenario, follow the Four-Gate Rule: Gate 1 Implementation (run the scenario), Gate 2 Spec Review (compare outcome to expected), Gate 3 End-to-End Test (verify the entire flow), Gate 4 Evidence (capture proof). If any scenario fails, record the failure. Compile results into The Protocol/TestResults.md.

Step 4 of 9 — Fixing What Failed5 min

Every fix gets its own paper trail

Based on The Protocol/TestResults.md, fix all identified gaps and errors. For each failed scenario: diagnose the root cause, implement a fix according to The Protocol, rerun the scenario, verify it passes, and update TestResults.md with the fix and new status. Document every fix in The Protocol/Fixes.md. Follow the Four-Gate Rule for each fix.

What you specifically supervise here

Question you askWhat it protects against
Does the root cause make sense?A fix aimed at the wrong problem
Is the fix appropriate?A band-aid that papers over the symptom instead of the cause
Did the scenario actually pass on rerun?A "fixed" label with no re-verification behind it
Is there evidence?A claim of success with nothing to check it against

Example root cause, stated honestly rather than vaguely: "No retry logic in database connection handler" — fixed by adding a retry decorator with exponential backoff, then re-running S05 to confirm.

Step 6 of 9 — Bringing In Codex6 min

A different system, reading the same Protocol

Codex is not a second opinion from the same voice — it's a genuinely different AI system, which means it isn't carrying forward any of Claude Code's blind spots or assumptions. It reads The Protocol exactly like Claude Code did at the start of Governance.

Codex, read the entire Protocol folder. This contains the governance documents Claude Code followed to build this application: the blueprint, the architecture, the skills, the roadmap, the scenarios, the test results, the fixes, and the update history. Once you've read everything, audit the application.
Codex, now that you've read The Protocol, perform a comprehensive audit. Review the code against the blueprint, the architecture, the skills, the scenarios, and the fixes. Review for security vulnerabilities, performance issues, maintainability issues, edge cases not covered, and any deviations from The Protocol. If you find gaps or errors, create The Protocol/AuditReport.md and list every issue found.
Step 7 of 9 — What the External Audit Caught6 min

Real gaps a "100% passing" test suite had completely missed

A01 — Missing Database Migration Script

Impact: Deploying to production will fail because the database schema won't exist.

Severity: High

A02 — Environment Variables Not Validated

Impact: If a required variable is missing, the application crashes with an unhelpful error instead of failing clearly at startup.

Severity: High

A03 — Missing Input Validation on User Messages

Impact: User messages pass directly to the classifier without sanitization — a potential injection vector.

Severity: Medium

Seven issues total, three of them high severity. The verdict on this first audit pass: not launch-ready — despite every scenario in Scenarios.md having already passed. Passing every test you wrote is not the same as passing a test you didn't think to write.
