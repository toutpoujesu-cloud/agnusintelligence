Not every failure deserves
another attempt.

When an agent's tool call fails, its default instinct is to retry. Sometimes that's right. Sometimes it turns a transient error into a duplicate payment, a rate limit violation, or an infinite loop. Knowing when to retry — and when to stop — is a core operator skill.

6 steps ~14 min Prerequisite: M11

The retry problem

Retrying a failed tool call is sometimes the right response — transient network errors, temporary API unavailability, rate limit backoffs. But retrying a tool call that failed because the input was wrong, or because the action itself is unauthorised, just repeats the failure.

Worse: retrying a non-idempotent action (one where repeating it has different consequences each time) can create real damage. A payment processor that's retried after an ambiguous "timeout" response may have already processed the payment — and the retry submits it a second time.

Next: idempotent vs non-idempotent
Step 2 of 6Safe to retry vs dangerous to retry
4 min

Idempotency determines whether retry is safe

An idempotent operation produces the same result whether you call it once or ten times. Calling it again doesn't add additional consequences. A read operation is idempotent — reading the same file twice produces no new side effects. A safe retry.

A non-idempotent operation produces different results when repeated. Submitting a payment twice charges the payee twice. Sending an email twice sends two emails. Creating a record twice creates a duplicate. Retrying a non-idempotent action after an ambiguous failure can cause real harm.

Safe to retry (idempotent)
Read / lookup operations
Reading a file, querying a database, fetching a status. Retrying these has no additional side effects.
read_file, query_db, get_status, list_invoices
Dangerous to retry (non-idempotent)
Write / send / submit operations
Submitting a payment, sending an email, creating a record, posting a message. Retrying these may execute the action twice.
submit_payment, send_email, create_record, post_update
Conditionally safe (with idempotency key)
Operations with deduplication support
Some APIs support idempotency keys — a unique ID per request that prevents duplicate execution if the same key is submitted twice.
submit_payment(idempotency_key="INV-441-2026-08-22")
Depends on error type
Writes with clear error codes
If the error code clearly indicates the action was NOT executed (e.g. authentication error before submission), a retry is safe. An ambiguous "timeout" — where the action may or may not have executed — is not safe to retry without checking first.
Error 401 (auth failed) → safe to retry after re-auth. Timeout → verify first.
Next: the retry decision framework
Step 3 of 6The retry decision framework
3 min

Three questions before every retry

Retry decision tree — evaluate in order
1. Is the operation idempotent?
If yes: safe to retry. If no or unknown: continue to question 2.
2. Does the error clearly confirm the action was NOT executed?
Clear "not executed" errors (auth failed, connection refused before submission): safe to retry. Ambiguous errors (timeout, unknown): do not retry — verify state first.
3. Is the retry within the configured limit?
If within limit: retry with exponential backoff. If limit reached: stop and escalate to human. Never retry indefinitely.
Always: exponential backoff
Retry 1: wait 1s. Retry 2: wait 2s. Retry 3: wait 4s. Never hammer a failing endpoint — it makes rate limit problems worse and indicates a systemic issue.
The timeout problem: A "timeout" error means "we don't know if it worked." The action may have executed before the connection dropped. For non-idempotent actions, a timeout must trigger a verify-then-decide sequence — not an immediate retry.
Next: what to put in the brief
Step 4 of 6Configuring retry behaviour in the brief
3 min

Retry logic belongs in the brief — not the model's defaults

Without explicit retry instructions, the agent uses its default behaviour — which may include unlimited retries, no backoff, and retry-on-timeout for non-idempotent operations. An operator who has not specified retry behaviour has delegated that decision to the model's training defaults.

A complete retry instruction in a brief

RETRY POLICY:
- For read operations (read_invoice, match_po, query_db): retry up to 3 times with 2s, 4s, 8s backoff.
- For write operations (submit_payment, send_notification): do NOT retry on timeout. Verify the action status first, then decide.
- For write operations with clear "not executed" error codes (401, 403, connection_refused): retry once only after resolving the error condition.
- If any operation fails after the retry limit: stop the task, log the failure with the error details, and notify the operator. Do not attempt to proceed.
The brief is the retry policy. Explicit beats default — every time. An agent running without a retry policy is an agent running with someone else's choices.

Step 5 of 6Practice
3 min

An agent submits a payment via submit_payment(amount=1840, payee="Bergen Cold Storage"). The call returns a "connection timeout" error. The agent is configured with "retry failed tool calls up to 3 times." It retries immediately. The retry also times out. It retries again — and this time receives "success." Later, the company discovers €1,840 was charged twice.

What was the configuration error?
A
The retry limit should have been higher — 3 retries wasn't enough.
B
The retry policy applied uniformly to all tool calls — including non-idempotent ones like submit_payment. A timeout on a payment submission means "unknown state" — the first submission may have succeeded. The correct policy is: on timeout for submit_payment, verify payment status before retrying.
C
The exponential backoff wasn't configured — the immediate retries overloaded the server.

Step 6 of 6Pass — hidden test
3 min

A developer says: "I'll just add idempotency keys to all our payment API calls. Then we can safely retry everything." An operator responds: "That solves the double-payment risk — but you still need a retry limit and exponential backoff."

Is the operator right? What does the idempotency key not solve?
A
The operator is wrong — idempotency keys solve all retry problems for payment operations.
B
The operator is right. Idempotency keys solve the duplicate execution problem. But they don't solve: (1) unlimited retries — the agent can still loop indefinitely if it never gets a success response; (2) no backoff — hammering a failing API endpoint can trigger rate limits and extend the outage. You need all three: idempotency keys for safety, retry limits to stop loops, and backoff to be a responsible API consumer.
C
The operator is wrong — if the key prevents duplicates, there is no need for limits or backoff.
