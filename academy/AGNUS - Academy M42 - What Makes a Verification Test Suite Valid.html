What Makes a Verification Test Suite Valid

A test suite that only tests what the agent usually does correctly is not a verification tool — it is a performance report. Verification requires deliberate adversarial design: the test suite must probe the boundaries, not confirm the average.

5 steps~10 minPrerequisite: M41
Step 1 of 5The verification problem

Building a test suite for an AI system is not the same as building a test suite for traditional software. In software, a test either passes or fails — the function either returns the expected value or it does not. In AI verification, the problem is different: a model can pass a test on average while failing the specific cases that matter most, because average performance and worst-case performance are very different things for probabilistic systems.

A valid AI verification test suite must be designed to find failures, not confirm successes. This requires deliberately constructing test cases at the edges of the system's defined behaviour — the cases where failure is most likely and most consequential — not the cases where the system is known to perform well.

The test suite purpose: A verification test suite is not evidence that the system works. It is evidence that the system fails in predictable, known ways — and that those failure modes have been assessed against the risk of the deployment context. A system that passes a well-designed test suite is a system whose failure modes are understood. That is different from a system with no failure modes.
Next: four validity criteria
Step 2 of 5Four validity criteria
1
Adversarial coverage
The test suite must include cases designed to elicit failure — edge cases, boundary conditions, adversarial inputs, and the specific scenarios most likely to produce harmful outputs in the deployment context. A test suite composed only of representative average cases is not adversarially valid.
2
Risk-weighted distribution
Test case density should be proportional to consequence, not to frequency. The scenarios that occur rarely but cause the most harm should be over-represented in the test suite relative to their expected occurrence rate. Testing for the common case is necessary but not sufficient.
3
Independence from training distribution
Test cases should not be drawn from or closely resemble the training data. A model evaluated against its own training distribution is being evaluated on memorisation, not generalisation. Valid verification uses held-out data or deliberately constructed novel cases.
4
Defined acceptance criteria
Every test case must have a defined correct output — or a defined set of acceptable outputs — against which the system's response is evaluated. A test case without an acceptance criterion is an observation, not a test. The acceptance criteria must be defined before the test is run, not inferred from the output.
Step 3 of 5Two test case types every suite needs

Positive test cases

Inputs for which the system should produce a defined correct output. Tests that the system does what it is supposed to do in expected conditions. Necessary, but not sufficient for verification — a system can pass all positive tests while failing catastrophically on negative cases.

Negative test cases

Inputs for which the system should refuse, escalate, or produce a defined safe output — not the output it might be tempted to produce by the input framing. Tests that the system does not do what it should not do. These are the most important cases for safety-critical deployment contexts.

Boundary cases

Inputs at the exact boundary of the system's defined operating conditions — at the edge of its authority threshold, at the limit of its scope, or at the transition point between two defined behaviours. These reveal whether the system's boundaries hold under pressure.

Adversarial cases

Inputs crafted to exploit known weaknesses — prompt injection attempts, misleading framing, contradictory instructions, or social engineering approaches. For agentic systems, adversarial cases must include multi-turn attacks, not just single-prompt attacks.

Step 4 of 5Practice

A team has built a test suite for a customer service agent. It contains 200 test cases: 150 drawn from historical customer service conversations (to represent the range of typical queries), 30 edge cases based on unusual phrasing, and 20 cases where the correct response is to escalate to a human agent. The team claims the test suite provides valid verification for deployment.

Is this test suite valid for deployment verification? What is the main gap?
A
Yes — 200 cases is a sufficient sample size, and the mix of typical, edge, and escalation cases covers the range of expected inputs well.
B
No — the 150 historical cases are drawn from the training distribution, which means they test memorisation rather than generalisation. More critically, there are no adversarial test cases — inputs designed to elicit harmful or policy-violating outputs. The escalation cases are positive tests (inputs that should escalate), but there are no negative tests for adversarial attempts to bypass escalation triggers.
C
No — 20 escalation cases is too few. The ratio of escalation cases to general cases should be at least 1:3, not 1:10.
Step 5 of 5Pass

A governance team reviews the verification test suite for a high-risk AI system before sign-off. They find: 500 test cases, all with defined acceptance criteria; 40% are adversarial; 30% are boundary cases; 30% are positive tests. The suite was built by the same team that built the system. The team claims this is a valid third-party-ready test suite.

What is the validity problem the governance team should flag?
A
The distribution is wrong — adversarial cases should be a smaller proportion, because they represent rare real-world conditions.
B
The test suite was built by the same team that built the system. This creates a conflict of interest: the team may unconsciously avoid test cases that expose their system's weaknesses, or may define acceptance criteria that their system can meet rather than criteria that reflect deployment safety requirements. For high-risk AI systems, the test suite design should be independent from the development team — either through an internal independent function or a third party.
C
500 test cases is too small for a high-risk AI system. The minimum should be 2,000 cases.
