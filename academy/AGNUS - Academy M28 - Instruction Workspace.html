The instruction workspace is
where governance is authored.

A governed agent is only as good as the instructions that govern it. The instruction workspace is the structured environment where you compose, test, and version-control agent instructions — treating them with the same rigour as the code they run alongside.

6 steps ~18 min Includes live instruction builder

Why instructions need a workspace

Agent instructions are written once and then silently govern agent behaviour for weeks or months. A brief written in a text chat with no version history, no review, and no testing is a governance liability. The instruction workspace treats briefs as governed artefacts: authored, reviewed, versioned, and tested before deployment.

At Level 4, you are responsible for maintaining the quality of instructions across your agent deployments — not just writing them for individual runs. That requires a disciplined workspace.

Next: the five workspace principles
Step 2 of 6Five workspace principles
4 min
Principle 1
Single source of truth
Every agent has one canonical instruction document. Not a chat history, not a shared document with track changes, not a file named "brief-final-v3." One versioned, owned document.
Principle 2
Version control
Every change is tracked, dated, and attributed to a person. "Who changed this and when?" must always be answerable. Rollback must be possible.
Principle 3
Review before deployment
No instruction change goes live without review by a second person. This is the instruction equivalent of a code review. One pair of eyes is not enough for instructions that govern consequential actions.
Principle 4
Test before deployment
New or changed instructions are tested against a standard set of scenarios (including edge cases) before going live. An instruction that hasn't been tested against a no-PO invoice hasn't been tested.
Principle 5
Scheduled review cadence
Instructions don't review themselves. A scheduled review cadence — monthly for high-consequence agents, quarterly for others — ensures instructions stay current as business context changes.
The test
Can you answer these?
Who authored this instruction? When was it last reviewed? What changed in v3? Has it been tested against a duplicate invoice scenario? If you can't answer these, you don't have a workspace — you have a text file.

Step 4 of 6Versioning and the review process
3 min

What a version record looks like

Every deployment instruction should have a version header. This is what makes governance traceable over time. Without it, "what was the instruction when the incident happened?" cannot be answered.

Version header format

AGENT: Invoice Processing Agent
VERSION: v3
EFFECTIVE: 2026-08-23
AUTHOR: Maja Lindqvist (Finance Operations)
REVIEWER: Tor Andersen (Finance Director)
CHANGES FROM v2: Threshold lowered from €500 to €250 per organisational standard update (2026-08-20). Duplicate detection escalation path added.
NEXT REVIEW: 2026-09-23
TEST STATUS: Tested against 6 scenarios including no-PO, duplicate, and above-threshold on 2026-08-22.
The review process: Author writes the change → reviewer reads it against the policy architecture (M27) and tests it against the standard scenario set → reviewer approves or returns → approved instruction gets a new version number and effective date → previous version is archived, not deleted.
Next: practice
Step 5 of 6Practice
3 min

An operator updates a customer service agent's instruction to change the escalation threshold: "route angry customers to human agents." The operator makes the change in a shared Google Doc, does not version it, does not send it for review, and deploys it the same day. Three weeks later, a complaint is raised about an incident where the agent failed to escalate an angry customer. The operator says: "I fixed the instruction three weeks ago — it should have been working." Legal asks for the instruction version that was active on the day of the incident.

Which workspace principles were violated, and what is the governance consequence?
A
Only the review principle was violated — the instruction should have been reviewed before deployment.
B
Three principles were violated: (1) Version control — no version record means the operator cannot prove what the instruction said on the day of the incident. (2) Review before deployment — unreviewed instruction deployed same day. (3) Single source of truth — a shared Google Doc with no versioning is not a governed instruction store. The governance consequence: the legal question "what was the instruction on the incident date?" cannot be answered. The instruction change may never be provable.
C
Nothing was violated — the operator has the authority to update the instruction for their own agent.
Final test
Step 6 of 6Pass — hidden test
3 min

A colleague argues: "Version control and review processes slow us down — we need to be able to update agent instructions quickly when business conditions change." An experienced governance lead responds: "The review process for a minor instruction change should take one hour, not one week. If it takes a week, the process is broken — but the answer is to fix the process, not to remove governance."

Who is right, and what is the key distinction?
A
The colleague is right — governance of instructions adds overhead that outweighs the benefits for fast-moving environments.
B
The governance lead is right. The issue is the design of the process, not the principle of governance. A well-designed review process for a minor instruction change — one reviewer, a defined scenario set, a version header — should take an hour. The solution to "governance is slow" is to design a faster governance process, not to remove governance. An unreviewed instruction change that causes an incident creates more delay than any review would have.
C
Both are partially right — governance should be applied proportionally, only to high-risk changes.
