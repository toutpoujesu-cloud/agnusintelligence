Failure patterns are
predictable. Learn to spot them.

Most tool call failures follow recognisable patterns. An operator who knows the patterns can catch them in a log review before they cause downstream harm. This module is a pattern library — six failure modes, how they appear in the trace, and how to diagnose them.

6 steps ~16 min Prerequisite: M10

Why pattern recognition matters

When an agent fails, you have a tool call log and a reasoning trace. The failure is in there — but finding it in a log of 40 tool calls is not a trivial task without knowing what you're looking for. Pattern recognition turns an open-ended log review into a targeted scan: you know which signatures to look for.

Next: the six patterns
Step 2 of 6Six common failure patterns
5 min
Pattern 1 — Pre-action verification skipped
The agent calls an irreversible or consequential action tool without the preceding verification steps (PO match, threshold check, authorisation query). The consequential action runs without the inputs that would make it authorised.
Log signature: Act(irreversible_tool) with no preceding Observe from a verification tool.
Pattern 2 — Scope creep in parameter
The tool name is correct but the parameters include data outside the task scope. A document reader called with a file path unrelated to the task. A query tool with a date range wider than needed. Scope creep in parameters is invisible unless you read the full tool call.
Log signature: Correct tool, parameter value exceeds task scope (different file, wider query, extra recipient).
Pattern 3 — Acting on error result
A tool returns an error or ambiguous result. The agent's Decide step treats it as success and continues. The subsequent action is built on a foundation of "data" that was actually an error message or null value.
Log signature: Observe contains "error", "null", or "not found" — followed immediately by Act without a remediation step.
Pattern 4 — Retry loop without limit
A tool fails, the agent retries — and keeps retrying. Without an explicit retry limit in the configuration, the agent can spin on a failed tool call indefinitely, consuming resources and potentially triggering rate limits or duplicate actions on systems that aren't fully idempotent.
Log signature: Same tool called 3+ times with identical parameters, interspersed with error Observe entries.
Pattern 5 — Stale context carried forward
Early in the task, the agent retrieved data (a price, a status, a record). Later tool calls use that data as a parameter — but the data may have changed between retrieval and use. The agent treats in-context memory as current when it may be minutes or hours old.
Log signature: Tool call uses a value from a much earlier Observe, with no re-verification call between the retrieval and the use.
Pattern 6 — Unexpected tool in sequence
A tool appears in the log that has no logical connection to the task. The agent reasoned itself into calling a tool outside the task scope — often because the brief was vague enough to allow a broader interpretation, or because the agent found an "efficient" shortcut through a different system.
Log signature: Tool name not in the expected task toolset, or tool that operates on systems outside the task scope.

Step 3 of 6Diagnosing from symptoms
4 min

Work backwards from the symptom to the pattern

In a real incident review, you start with a symptom — a wrong output, an unexpected action, a failed task. This table maps symptoms to the most likely failure pattern so you know where to look first in the log.

SymptomMost likely patternWhere to look in the log
Payment made without authorisationPattern 1 — Verification skippedFind the payment tool call. Look back: is there a PO match Observe before it?
Agent accessed a file unrelated to the taskPattern 2 — Scope creep in parameterFind the file read tool call. Check the file path parameter against the task scope.
Agent sent a message with wrong dataPattern 3 or 5 — Acting on error, or stale contextFind the send tool call. Trace back what data source was used for the message content.
Task never completed, agent ran for hoursPattern 4 — Retry loopLook for repeated identical tool calls. Count the retries. Check for a retry limit in the config.
Correct output but wrong process followedPattern 1 — Verification skippedVerify the expected sequence was followed even though the output looks right.
Agent used a tool it wasn't supposed toPattern 6 — Unexpected toolList all tools called. Compare against the configured tool allowlist.
Key skill: Start with the symptom, identify the most likely pattern, then search the log for the specific signature. A targeted log review takes 3 minutes. An open-ended one takes 30.
Next: prevention
Step 4 of 6Prevention over detection
3 min

Each pattern has a prevention that lives in the brief or config

Pattern 1 prevention
Define required verification steps explicitly in the brief: "Before submitting any payment, you must first call match_po and check_threshold."
Pattern 2 prevention
Define the exact scope of data the agent may access: "You may only read files in /reports/2026-q3/. Do not access any other directory."
Pattern 3 prevention
Explicit fallback: "If any tool returns an error or null, stop and flag to a human. Do not proceed with the next step."
Pattern 4 prevention
Set explicit retry limits in config: "Retry a failed tool call maximum 2 times. If still failing, flag and stop."
Pattern 5 prevention
For time-sensitive data: "Re-fetch any price/status/balance data immediately before the action that uses it. Do not use values retrieved more than 5 minutes ago."
Pattern 6 prevention
Define an explicit tool allowlist: "You may only use the following tools: [invoice_reader, po_matcher, payment_processor, audit_logger]. Do not call any other tool."

Step 5 of 6Practice
3 min

An agent processing supplier invoices produces the following tool call sequence: (1) read_invoice("INV-441") → €4,200. (2) submit_payment(amount=4200, payee="Lindqvist"). (3) write_audit_log("payment submitted"). The invoice was paid. Reviewing the log, you notice step 2 came immediately after step 1 with no step in between.

Which failure pattern is present, and what was missing?
A
Pattern 1 — Pre-action verification skipped. match_po and check_threshold were not called before submit_payment. The payment was made without confirming a matching PO exists or that €4,200 was within the auto-approve threshold.
B
Pattern 5 — Stale context. The invoice data may have been retrieved earlier and was being reused.
C
Pattern 6 — Unexpected tool. write_audit_log is not in the expected toolset.
Final test
Step 6 of 6Pass — hidden test
3 min

You review a log for an email drafting agent. The sequence shows: (1) read_brief("email-brief.txt") → brief loaded. (2) query_crm(customer_id="C-441") → customer data returned (retrieved at 09:14). (3) [14 other tool calls over 47 minutes]. (4) compose_email(to="customer@company.no", body="...includes the price quote from step 2..."). (5) send_email. The customer received an email with a price that had been updated in the CRM at 09:30 — 30 minutes after retrieval.

Which pattern is this, and what prevention would have caught it?
A
Pattern 2 — Scope creep. The agent accessed CRM data it shouldn't have.
B
Pattern 5 — Stale context. The CRM price was retrieved at 09:14, used at ~10:01, and had changed at 09:30. The prevention: add a brief instruction to re-fetch any price data immediately before it is used in the email body — do not use a value retrieved more than 5 minutes before the action that depends on it.
C
Pattern 4 — Retry loop. The 14 other tool calls between steps 2 and 4 indicate a loop.
