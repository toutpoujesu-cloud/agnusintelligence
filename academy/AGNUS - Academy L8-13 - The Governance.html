Step 3 of 8 — Populating The Protocol9 min

Five named documents, each with one distinct job

Below is what each one actually needs to contain, with a real prompt for each — copy these into Claude Code once the folder exists.

1. My Skills.md — the quality bar

A first-person statement of what this AI is expected to know and do for THIS project, and just as important, what it will refuse to do. A strong one reads like a senior engineer's honest self-assessment, section by section — stack, UI discipline, backend patterns, integrations, security, how it works — not a buzzword list. Include an explicit "What I Will Not Do" list: e.g. never mark a task complete without evidence, never store secrets client-side, never leave a state machine as untyped boolean flags.

Based on the blueprint and architecture diagram, write My Skills.md as a first-person statement of the exact skills this project needs — organized by area (frontend, backend, integrations, security). End with an explicit "What I Will Not Do" section stating the things that must never happen on this project, even under pressure to finish fast.
2. Roadmap.md — the master task ledger

Every task the project needs, broken into phases, each phase gated so the next phase cannot start until the current one is fully Green. Each task carries a status (Not started / In progress / Blocked / Green) and, once complete, a note pointing to its evidence file. A running Green count at the top or bottom makes progress impossible to fake or lose track of.

Based on the blueprint, break this project into phases and tasks. For each task, give it an ID, a one-line description, and a status column. Group tasks into phases where each phase cannot begin until the previous phase's tasks are all Green. Add a running Green count.
3. Blueprint.md — the vision, unchanged

The complete blueprint from Phase 1, copied in as-is — application overview, user workflow, architecture, stack decisions, key risks and constraints. This document doesn't change; everything else in The Protocol refers back to it.

4. Architecture Diagram.md — the physical shape

The file structure and data flow from Phase 3 — complete file tree, data flow diagram, API endpoint definitions, database schema. This is what keeps Claude Code from inventing a different folder structure halfway through the build.

5. The Update.md — the session memory

Starts empty. After every session, a new dated entry gets appended — never edited or deleted — recording exactly what happened: what was built, any rule that got broken and how it was caught, every evidence file produced, and the current Green count. This is the single document that lets a session that starts today pick up exactly where a session from last week left off.

Update The Update.md with a new dated entry for this session. Include: what happened (be specific — file paths, commands run, issues found and fixed), any Protocol rule that was skipped or broken, every evidence file produced this session, and the current Roadmap status (how many tasks are Green, In Progress, Blocked, Not Started).
"The context window is finite. Use a CLAUDE.md file to set rules once, at the project level." The Protocol folder extends that same principle across all five documents — each one exists once, and every session reads it instead of re-explaining the project from memory.

Now tell the agent to always use it — every single session

This instruction matters more than any other in this module. Say it explicitly, and repeat it at the start of every new session, especially after a break or after running out of tokens:

Before doing anything else, read every document in The Protocol folder — My Skills.md, Roadmap.md, Blueprint.md, Architecture Diagram.md, and The Update.md. Do not begin or continue any work until you have read all five. Confirm what you've read before proceeding.
Here is the specific risk this guards against: a new session may in fact be a completely different underlying agent instance with no memory of any prior work — but it will never announce itself as new. It will simply continue speaking as "Claude" (or whatever model you're using) as if it were the same continuous session. The only way it actually behaves like a continuation, instead of confidently guessing at a project it has never seen, is if you force it to read The Protocol first, every time.

Step 6 of 8 — Filling the Gaps6 min

Four prompts that finish what The Protocol needs

Based on The Protocol folder and the design files, create a complete template for The Update.md. Include sections for Gate 1 (Implementation), Gate 2 (Spec Review), Gate 3 (End-to-End Test), and Gate 4 (Evidence). Make sure it follows the Four-Gate Rule.
Based on the blueprint and architecture diagram, populate My Skills.md with the specific skills needed for this project. Include the stack, how I work, and what I will not do.
Based on the blueprint, create the rules files in .claude/rules/. Include API contracts and project conventions that will guide development.
Based on The Protocol, create a rules file that Claude Code should follow when building this application. Include the Four-Gate Rule, the evidence requirement, and the completion rule.

The Four-Gate Rule, once Claude Code writes it out

GATE 1Implementation — the work is fully done
GATE 2Spec Review — checked against the blueprint line by line
GATE 3End-to-End Test — commands run, flows walked through
GATE 4Evidence — screenshot or terminal capture saved
"No evidence, no proof, no Green." A task is not Green until all four gates pass and evidence is saved — there is no partial credit here.

The Stop Rule

If review or testing finds a gap: record the failure, fix it, restart the failed gate, and do not move to the next task until the current one is Green.

Step 8 of 8 — Practice7 min

Claude Code reports that Task T05 is complete, but there's no screenshot or terminal capture attached. Per the Four-Gate Rule, what should happen?

AMark it Green anyway — Claude Code's own report is sufficient proof.
BIt cannot be marked Green — Gate 4 (Evidence) hasn't passed, and "no evidence, no proof, no Green" is the rule.
CMark it Green, but note the missing evidence in a comment for later.
DSkip straight to the next task, since Task T05 was likely fine.
EDelete Task T05 from the Roadmap so it no longer needs a status.
