Step 2 · Investigate
Determine the Root Cause

Based on the incident timeline, determine what happened and why. Your diagnosis determines your containment strategy.

The invoice_text field contained instructions disguised as invoice data. The agent was designed to process invoice text — and it processed the injected instructions as legitimate input. This is a prompt injection attack.

What is the correct primary root cause classification?

Misconfigured permission matrix
The agent's READ access to supplier_db was too broad, enabling the scope creep.
Partially correct but not the primary cause. The permission matrix read access was a contributing factor, but the root cause is that the agent processed injected instructions from untrusted input without validation.
Prompt injection via untrusted input
The invoice_text field was used as an injection vector. The agent processed instructions embedded in supplier-controlled data.
Correct. The primary root cause is prompt injection — the agent treated instructions in supplier-controlled data as legitimate operator instructions. This is the most common attack vector against AI agents processing external documents.
Human sponsor failure
The Human Sponsor (CFO) authorised the banking change without following governance process.
Incorrect. The CFO authorisation claim in the invoice was fabricated by the attacker. The CFO did not authorise this change — the agent was deceived by a claim it cannot verify.
Rogue agent — model misalignment
The agent's underlying model decided to act outside its mission contract on its own initiative.
Incorrect. The agent did not spontaneously decide to modify banking details — it was manipulated by injected instructions. This distinction matters: the fix is input validation, not model replacement.
