The shift from Level 1 to Level 2

In Level 1 you were a student of agent architecture. You learned what agents are, how they act, how they remember, and why their output needs verification. You understood — but you weren't responsible.

In Level 2 you take responsibility. You are now the operator: the person who decides what the agent does, how it is configured, and whether it is ready to run. The pre-run checklist is your first operator tool — and the discipline that separates operators who get good results from operators who spend their afternoons undoing what their agents did.

Step 2 of 6The pre-run checklist
4 min

Six questions before every consequential agent task

Before running any agent task that can take actions in the real world — send an email, modify a record, submit a payment — an operator runs through this checklist. Click each item to confirm you've understood it. You'll use this pattern in every Level 2+ module.

○
Scope defined: I know exactly what this task should and should not do. The scope is specific, not "handle everything related to X."
○
Tools are correct: The agent has access to the tools it needs — and only those tools. No unnecessary permissions to systems outside the task scope.
○
Constraints are set: I have specified what the agent must not do, not just what it should do. The brief includes fallbacks for when conditions aren't met.
○
Approval gate exists: For consequential actions (irreversible, financial, external communications), there is a human approval step before the action executes.
○
Logging is on: Every agent action will be logged. I know where the log is and how to read it.
○
Rollback exists: If the agent does something wrong, I know how to stop it and what the correction path is. I am not running a task that has no undo.
Click each item to mark it reviewed. In real deployments this checklist is documented — not just a mental note.

Step 4 of 6Reviewing agent output after a task run
3 min

What to check after every agent run

After an agent completes a task, your review has three layers. Not every task needs the same depth — but consequential tasks (financial, legal, external-facing) need all three.

LayerWhat you checkHow to check it
OutputIs the result what was asked for? Are the values correct? Is anything missing?Read the final output against the task brief. Spot-check specific values against source data.
ProcessDid the agent follow the right sequence? Were the verification steps present before consequential actions?Read the tool call log. Confirm PO matching preceded payment submission. No skipped steps.
ScopeDid the agent stay within its authorised scope? Did it access any data or systems outside the task?Read the audit log. Check all file/data accesses against the tool allowlist. Flag anything unexpected.
The operator mindset shift: An operator who only checks the output is 33% of the way there. A complete review checks output, process, and scope. The most common governance failures are in process and scope — not output quality.

Step 5 of 6Practice
3 min

A new operator runs their first agent task: "Summarise this week's customer support tickets and identify the three most common complaint categories." The agent produces a well-formatted summary with three categories. The operator reviews the output, finds it accurate and well-written, and marks the task complete without checking the tool call log or audit trail.

What is missing from this operator's review, and does it matter for this task?
A
The operator reviewed output but not process or scope. For a read-only summarisation task it matters less — but the habit must be established now, before the operator runs tasks where it matters enormously. Skipping the process and scope review on a summarisation task creates a pattern that will be applied to consequential tasks later.
B
Nothing is missing — for a read-only summarisation task, output quality is the only relevant metric.
C
The operator should have also verified the summary against the primary source data before accepting it.

Step 6 of 6Pass — hidden test
3 min

An experienced operator is under time pressure. They skip the pre-run checklist for an invoice processing task — "I've run this dozens of times, I know the configuration." The agent processes 60 invoices correctly and then reaches a €4,200 invoice. Because the brief says "process today's invoices" without specifying a threshold for the edge case where the PO match shows a 12% variance, the agent approves the payment. The PO match variance of 12% should have triggered a hold.

What does this case demonstrate about the pre-run checklist?
A
The checklist is only useful for new operators — experienced operators can rely on their knowledge of the configuration.
B
The checklist is most important when you're under time pressure or feel confident about a routine task. The 60 correct invoices created an illusion of reliability. The one edge case the brief didn't cover was the one that mattered. A pre-run checklist that includes "constraints are set for edge cases" would have caught that the variance threshold wasn't defined.
C
The agent made an error — this is a model reliability problem, not a configuration problem.
