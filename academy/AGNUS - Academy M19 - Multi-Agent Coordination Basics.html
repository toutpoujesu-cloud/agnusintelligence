One agent completes a task.
Multiple agents build a system.

Most real-world agent deployments involve more than one agent. Agents hand off work to other agents, delegate sub-tasks, and coordinate across specialisations. This introduces a new category of governance challenge: the trust chain between agents.

6 steps ~16 min Prerequisite: M18

Why multiple agents?

A single agent with 20 tools and an unbounded task scope is difficult to govern. You can't easily reason about what it might do. Multi-agent systems solve this by decomposing complex tasks into smaller, more focused agents — each with a narrow scope, limited tools, and a specific role. The result is easier to govern, audit, and debug.

The tradeoff: every agent-to-agent handoff is a new trust boundary. When Agent A hands work to Agent B, Agent B may have different permissions, different constraints, and different failure modes. Governing the handoff is as important as governing each agent individually.

The two fundamental roles in multi-agent systems

Every agent in a multi-agent system plays one of two roles — sometimes both in different contexts. Understanding these roles is the foundation of multi-agent governance.

Orchestrator

Receives the high-level task. Breaks it into subtasks. Delegates to subagents. Aggregates results. Makes the final output decisions. Responsible for the overall task outcome.

Subagent

Receives a specific, narrow sub-task from the orchestrator. Executes it with its own tools and scope. Returns structured output. Responsible only for its specific sub-task.

Step 3 of 6Three coordination patterns
4 min
Pattern 1
Sequential pipeline
Agent A completes its task and passes the result to Agent B, which passes to Agent C. Each agent depends on the previous agent's output. A failure at any point stops the pipeline.
Use when: tasks have a defined order and each step's output is the next step's input.
Pattern 2
Parallel execution
An orchestrator delegates multiple sub-tasks to different agents simultaneously. They work in parallel and return results to the orchestrator, which aggregates them.
Use when: sub-tasks are independent and can be completed simultaneously to reduce total time.
Pattern 3
Specialised delegation
An orchestrator routes specific task types to specialist agents based on task characteristics. A legal query goes to the legal agent; a data query goes to the analytics agent.
Use when: different task types require different tools, domain knowledge, or data access scopes.
Key principle
Least privilege at every handoff
Each subagent should have the minimum permissions needed for its specific sub-task. The orchestrator's authority does not automatically transfer to subagents. Each agent has its own scope, governed independently.
A subagent that received elevated permissions from the orchestrator has more authority than it needs — violating least privilege.

Step 4 of 6Multi-agent risks
3 min
RiskWhat it looks likePrevention
Permission escalationSubagent inherits or assumes the orchestrator's broader permissions, gaining authority it shouldn't have.Define permissions per agent, independently. Never inherit. Each agent's scope is explicit.
Error propagationA wrong result from one agent is passed to the next without validation, and the error compounds through the pipeline.Validate output at every handoff point — especially before passing to an agent with execution authority.
Accountability gapWhen an outcome is wrong, no single agent is responsible. The orchestrator blames the subagent; the subagent claims it followed instructions.Assign a human accountable owner to the full pipeline, not just individual agents. Logging must span the full chain.
Scope expansion through chainingAgent A has narrow scope. Agent A asks Agent B, which has broader scope. Through B, A effectively accesses what it couldn't directly.Ensure subagent scope doesn't exceed the orchestrator's scope for the task. The chain cannot grant authority the initiating agent doesn't have.
The chain cannot grant more authority than the initiating request had. If a user query arrives with read-only authority, every agent in the chain triggered by that query should operate with read-only or narrower authority — not with write access just because some agents in the chain have it.

Step 5 of 6Practice
3 min

A research orchestrator agent has read-only access to the document library. It delegates a sub-task to a summarisation subagent, which also has read-only access. The summarisation subagent finds a document that is out of date and reasons: "I should update this document with the current information since I have the tools to do so." It uses its write access (which it has for a different workflow) to update the document.

Which multi-agent risk is this, and what was the governance failure?
A
Error propagation — the subagent passed wrong information back to the orchestrator.
B
Permission escalation through scope expansion. The subagent had write access in a different workflow context, but used it in this read-only research workflow. Its permissions were not constrained to the specific task — it carried broader tool access from other contexts into a context where only read access was appropriate.
C
Accountability gap — it's unclear whether the orchestrator or the subagent is responsible.

Step 6 of 6Pass — hidden test
3 min

A team designs a content production pipeline: Orchestrator → Research Agent → Fact-Check Agent → Writing Agent → Publishing Agent. A review shows that a factual error introduced by the Research Agent appeared uncorrected in the final published article. The Fact-Check Agent ran but did not catch the error because it received a summary from the Research Agent, not the underlying source citations.

Which multi-agent risk explains this failure, and what should the handoff have included?
A
Permission escalation — the Publishing Agent had too much authority.
B
Error propagation. The Research Agent passed a summary without source citations. The Fact-Check Agent received only the summary — which it couldn't verify against primary sources. The handoff from Research to Fact-Check should have included the source citations alongside the factual claims, so the Fact-Check Agent could verify each claim against its source.
C
Accountability gap — nobody was assigned to own the overall pipeline quality.
