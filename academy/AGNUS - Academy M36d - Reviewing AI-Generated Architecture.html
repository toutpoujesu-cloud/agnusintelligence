The architecture review is
your last chance before the build.

After scaffolding and before writing business logic, a structured architecture review catches governance gaps, security issues, and structural problems while they are still cheap to fix. This module gives you the review framework and the structured review checklist.

6 steps ~14 min Prerequisite: M36c

When to review and what you are reviewing

The architecture review happens after the scaffold is complete and before business logic is written. At this point, the structure exists but nothing irreversible has happened. You are reviewing the data model, the API surface, the access controls, and the agent integration points — not the code quality.

A code review (checking that the logic is correct) is a different discipline, covered in M36e. The architecture review checks that the structure is correct — that the right governance hooks are in place and the right boundaries are established.

Next: six review categories
Step 2 of 6Six architecture review categories
4 min
1
Access control completeness
Every API endpoint has authentication. Every authenticated endpoint has role-based authorisation. No endpoint returns more data than the role is permitted to see.
Questions: Can an unauthenticated user call any endpoint? Can an AP team member see a finance director's approval history? Can an agent endpoint return personal data the agent doesn't need?
2
Data model governance
Personal data is in a separate table with retention constraints. The audit log table is append-only with no UPDATE or DELETE permissions. Sensitive fields are not mixed with operational fields.
Questions: Is there a separate personal data table? Does the audit log table have a constraint preventing modification? Are there explicit retention policies on each table?
3
Agent boundary definition
Agent access points are defined and scoped. The agent calls data through the API, not directly. Agent output endpoints require human confirmation before any consequential action.
Questions: Are agent endpoints separate and clearly identified? Do they return minimum necessary data? Is there a stub for human confirmation before any agent output creates consequences?
4
Approval gate placement
Approval gate stubs exist in the logic layer. No consequential action endpoint can be called without passing through an approval check. The approval check is not in the UI layer.
Questions: Is there a logic-layer function for each approval gate? Does it raise an error (not return a warning) when approval is required but absent?
5
Error handling structure
Every endpoint has defined error responses. Agent tool failures return structured errors (not silent nulls). Retry limits are configurable at the configuration layer.
Questions: Does every endpoint return a typed error for authentication failure, authorisation failure, and data not found? Can the agent's retry limit be configured without a code change?
6
Configuration vs. code separation
Thresholds, escalation targets, retry limits, and approval policies are in configuration files, not hardcoded. This means governance changes don't require code deployments.
Questions: Is the auto-approve threshold in a config file or hardcoded? Can the escalation email address be changed without a code change?

Step 4 of 6The configuration vs. code principle
3 min

Governance values in code require code deployments to change

A hardcoded threshold (AUTO_APPROVE_THRESHOLD = 500 in the logic file) can only be changed by modifying code, testing the change, and deploying a new version. This means a governance decision — the Finance Director decides to lower the threshold to €250 — requires a software deployment cycle.

A threshold in a configuration file (config.py, environment variable, or configuration table in the database) can be changed by updating the config, which can be done by a non-developer with appropriate access. This is the correct governance model: governance decisions are made by the governance owner, not by developers.

The review instruction: "Confirm that all approval thresholds, escalation targets, retry limits, and approval policies are in the configuration layer — not hardcoded. Any value that a governance owner might need to change should not require a code deployment."

Step 5 of 6Practice
3 min

A review of an AI-generated scaffold finds that the escalation_email field is hardcoded in the escalation function as "ap-lead@nordvik.no". The reviewer flags this. The developer says: "That's the correct email — why does it matter where it's defined?"

Why does the reviewer's concern matter?
A
Hardcoded emails are a security risk — they could be discovered in code reviews.
B
When the AP team lead changes — person leaves, role is restructured, email changes — the escalation path breaks silently. Updating it requires a code change, code review, and deployment. With the email in config, the governance owner updates the config file with no code change required, and the escalation path is immediately current. Governance values must be in config so governance owners can maintain them.
C
The email should be in the database, not in config, so it can be updated through the UI.

Step 6 of 6Pass — hidden test
3 min

A team skips the architecture review because "the scaffold looks clean and we're under time pressure." They proceed to business logic. Three weeks later they discover the agent endpoint returns full invoice records including supplier contact details (personal data), and the agent has been processing and logging this data. They now need to: (1) remove personal data from agent logs that shouldn't be there, (2) modify the endpoint, (3) audit what the agent did with the data.

Which category of the architecture review would have caught this, and what is the governance principle illustrated?
A
Category 1 — access control completeness would have caught the agent endpoint returning too much data.
B
Category 3 — agent boundary definition. The review question "do agent endpoints return minimum necessary data?" would have flagged the personal data fields in the agent response. The governance principle: a problem found in the architecture review costs an afternoon to fix. The same problem found three weeks into the build, after the agent has been processing data, costs a data subject rights audit, log remediation, and a GDPR accountability review. Review cost scales with how late the review happens.
C
Category 2 — data model governance would have caught the personal data being accessible to agents.
