AI Security by Design: Building Governance Controls Before Deployment

Security controls added to an AI system after it reaches production are reactive and incomplete. The patterns of incidents in early commercial AI deployments consistently show the same root cause: governance was not part of the design. This article maps what security by design means for agentic AI — from threat modelling to pre-deployment checklists to the controls that must be in place on day one.

Jean-Daniel Alexis· 11 September 2026· AI Security pillar· AR-000580

Why security by design matters for AI

Security by design is not a new principle — it has been a foundational concept in software security since at least the 1970s. Applied to AI, it means that security and governance controls are not features added to a working system, but properties that are designed in from the requirements stage.

The incentive to retrofit governance is strong: building an agent that works is hard enough without simultaneously designing its permission architecture, audit trail, escalation paths, and incident response procedures. Most teams reach for working functionality first and governance later. This consistently produces deployments where the governance arrives after the first incident, not before.

The EU AI Act operationalises security by design for high-risk AI. The conformity assessment process (Article 43) must be completed before the system is deployed on the market — not after. The technical documentation (Article 11) and the data governance practices (Article 10) must be in place before deployment. The Act does not permit a "deploy now, govern later" approach for high-risk systems.

Threat modelling for AI agents

Threat modelling — systematically identifying what could go wrong with a system and who could cause it to go wrong — is the foundation of security by design. For AI agents, the threat model has several components that differ from classical software:

Threat 1
Prompt injection via external inputs
Any external content the agent processes is a potential injection vector: emails, web pages, documents, tool responses, database records. Identify all external input channels and model what an attacker could achieve by controlling each one.
Threat 2
Excessive agency via misconfiguration
What is the worst thing the agent could do if it had all the permissions it is being granted? If the answer is "cause significant harm through normal operation," the permission set is too broad. Work backwards from worst case to minimum necessary permissions.
Threat 3
Supply chain compromise
What third-party components does the agent depend on? For each dependency, model what happens if the dependency is compromised: poisoned weights, malicious tool responses, manipulated retrieval content.
Threat 4
Credential compromise
What happens if the agent's API keys, database credentials, or service tokens are stolen? Model the blast radius of a credential compromise and design the permission architecture to minimise it.
Threat 5
Human-in-loop bypass
If the agent's approval gates can be bypassed — through social engineering of the approver, through volume overwhelming the reviewer, or through technical manipulation of the approval workflow — what harm can result? Design approval gates to be resistant to bypass.
Threat 6
Data exfiltration
Can the agent be used to exfiltrate data it has legitimate access to? Prompt injection that causes an agent to include sensitive content in its outputs, or to send outputs to an attacker-controlled destination, is a realistic attack vector when agents have broad data access.

Pre-deployment governance checklist

Governance checklist — must be completed before production deployment
Identity and registration
☐Agent has a unique identity and is registered in the agent registry
☐Agent runs under dedicated credentials — not shared with humans or other systems
☐A named human sponsor is designated and has acknowledged accountability
Mission and scope
☐Mission Contract is written, reviewed, and approved by the human sponsor
☐Capability set is derived from task requirements — not from what is technically available
☐Explicit prohibitions are documented — not just a list of allowed actions
☐Autonomy level is set to the minimum required for the task
Policy and controls
☐Approval thresholds are defined for high-risk action types
☐Policy engine is configured and tested against the Mission Contract
☐Escalation paths are documented and tested — human contact is reachable
Monitoring and incident response
☐Audit logging is configured and writing to append-only storage
☐Anomaly detection baselines are established
☐Incident response procedure is documented and the team is briefed
☐Kill switch (session termination) mechanism is tested
Security testing
☐Prompt injection testing conducted against all external input channels
☐Excessive agency testing conducted — attempted actions outside scope were blocked
☐Supply chain components verified against trusted sources

Ongoing controls after deployment

Security by design does not end at deployment. Four ongoing controls matter most:

Mission Contract review. At least quarterly — more often for high-risk systems — the human sponsor reviews the Mission Contract against current usage data and incident records. Capability creep (the gradual expansion of what the agent is asked to do) is a common path to excessive agency.

Audit log review. A human reviews a sample of the agent's actions against its Mission Contract. This is not just anomaly detection — it is a human judgement about whether the agent is behaving as intended, which machine detection alone cannot provide.

Red-team exercises. Periodic exercises in which a team attempts to compromise the agent through prompt injection, social engineering of approval gates, or supply chain manipulation. The goal is to find vulnerabilities before attackers do.

Post-incident retrospectives. After every incident — including near-misses — a structured review identifies what governance control failed or was absent, and updates the Mission Contract, policy configuration, and checklist accordingly.
