Supply Chain Attacks on AI Systems: How Third-Party Models and Tools Become Attack Vectors

Every AI system depends on components it did not build: foundation models from third-party providers, fine-tuned weights from open repositories, datasets from external sources, APIs from third parties, and tools that call external services. Each dependency is a potential supply chain attack vector. This article maps the threat landscape and the controls that reduce exposure.

Jean-Daniel Alexis· 11 September 2026· AI Security pillar· AR-000550

The AI supply chain threat landscape

Classical software supply chain attacks target dependencies: malicious code inserted into a library, a package manager poisoned, a build pipeline compromised. AI supply chain attacks follow the same logic but operate across a broader and less well-understood dependency surface.

The AI supply chain includes: the foundation model itself (weights, training data, alignment process); fine-tuning datasets and procedures; embedding models; retrieval databases and their contents; tools and APIs the agent calls; plugins and extensions; and the infrastructure that serves the model. Each layer has been successfully attacked in practice.

What makes AI supply chain attacks particularly insidious is that the effects may be subtle and delayed. A backdoor in a foundation model may only activate on specific trigger inputs. Poisoned training data may produce systematically biased outputs rather than dramatic failures. A compromised retrieval database may return attacker-controlled content only when certain queries are made. None of these appear in standard functional testing.

The four primary attack vectors

Vector 1
Poisoned training data
Attacker inserts malicious examples into training data to influence model behaviour. Effects may include backdoors (specific inputs trigger harmful outputs), systematic bias, or capability degradation. Particularly relevant for fine-tuned models using open or third-party datasets.
Vector 2
Compromised model weights
Open-weight models shared via public repositories (Hugging Face, GitHub) may be modified before download. The modification may be invisible to standard evaluation because it only activates on trigger inputs. Weight hashing alone is insufficient — the hash must be verified against a trusted source, not just the repository.
Vector 3
Malicious tool responses
When an agent calls a third-party API or reads from an external data source, the response may contain embedded instructions designed to manipulate the agent's subsequent actions — indirect prompt injection delivered via tool call response. The agent treats the attacker-controlled content as legitimate tool output.
Vector 4
Retrieval database poisoning
In RAG (retrieval-augmented generation) systems, the retrieved content is incorporated into the model's context. An attacker who can write to the retrieval database can insert content that steers the model's outputs when specific queries are made — without modifying the model itself.

Governance and technical controls

ControlWhat it addressesHow to implement
Model provenance registry Compromised weights, unverified sources Maintain a registry of all foundation models in use, their source, version, download hash, and the trusted source the hash was verified against. Never trust a hash verified only against the repository where the file was downloaded.
Dataset provenance documentation Poisoned training and fine-tuning data Document the provenance, collection methodology, and known biases of all datasets used for training or fine-tuning. For fine-tuning, prefer closed, verified datasets over open community contributions.
Tool response sandboxing Malicious tool responses / indirect prompt injection Treat all tool call responses as untrusted external input. The model should not have authority to take actions based solely on instructions embedded in tool responses. A policy layer should evaluate proposed actions before execution, regardless of their source.
RAG content integrity checks Retrieval database poisoning Apply content integrity validation to retrieved documents. Maintain a known-good hash of retrieval database contents and alert when unverified content is retrieved. For high-risk queries, require human review of retrieved content before it influences the model's output.
Third-party vendor assessment All external dependencies Assess AI-specific supply chain risks for all third-party providers: model providers, API providers, dataset sources, plugin developers. The EU AI Act's technical documentation requirements (Article 11) extend to information about third-party components used in the system.

What regulation says about supply chain security

The EU AI Act addresses supply chain security implicitly through its technical documentation (Article 11) and conformity assessment (Article 43) requirements. Providers of high-risk AI must document the data used to train and test the system, including data governance practices. For models using third-party training data, this documentation requirement applies to the third-party data as well as first-party data.

The EU Cyber Resilience Act (CRA), which entered into force in December 2024 and will apply from December 2027, explicitly addresses software supply chain security for connected products. AI components embedded in products within CRA scope must comply with its supply chain requirements — including security updates, vulnerability disclosure, and software bill of materials (SBOM) documentation.

NIST's AI RMF Playbook addresses supply chain risk in its GOVERN 1.7 and MAP 5.1 actions, requiring organisations to document and evaluate risks from third-party AI components. The practical requirement is a maintained inventory of all AI supply chain dependencies and a periodic reassessment of their security posture.
