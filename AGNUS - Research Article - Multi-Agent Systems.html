Multi-Agent Systems: Coordination, Trust and Governance

When multiple AI agents interact — one orchestrating, others executing — accountability does not automatically follow. This article examines how trust models, delegation chains, and conflict resolution work in multi-agent architectures, and what governance controls actually close the accountability gap.

Jean-Daniel Alexis · 11 September 2026 · AI Agents pillar · AR-000510

The anatomy of a multi-agent system

A multi-agent system (MAS) consists of at least two AI agents that communicate, share information, or delegate work to each other to accomplish tasks a single agent could not perform alone — or that a system designer chose to distribute for modularity, specialisation, or scale.

The most common pattern in commercial deployments today is the orchestrator-worker model: one agent receives a high-level task, decomposes it into sub-tasks, and dispatches those sub-tasks to specialised worker agents. The orchestrator may be an AI model itself, or it may be a deterministic routing system. The workers may operate in parallel or in sequence, each producing outputs that feed back into the orchestrator.

A second pattern is the peer-to-peer model: agents communicate with each other as equals, each capable of initiating requests and receiving them. This pattern is common in research and simulation contexts and is emerging in production as agent-to-agent (A2A) protocols standardise.

A third, underappreciated pattern is the human-in-the-loop hybrid: the system includes both AI agents and human agents, with the AI agents handling high-volume routine work and routing exceptions to humans. This is the most common pattern in regulated industries, where an AI agent cannot make final decisions on consequential matters.

Pattern 1
Orchestrator–Worker
One agent decomposes a task and delegates sub-tasks to specialised workers. The orchestrator aggregates results. Common in enterprise automation pipelines.
Pattern 2
Peer-to-Peer
Agents communicate as equals, each capable of initiating requests. Emerging in production via A2A protocols. Governance is more complex — there is no single authority.
Pattern 3
Human-in-the-Loop Hybrid
AI agents handle routine volume; humans receive escalations and make final decisions on consequential matters. Required by EU AI Act Article 14 for high-risk AI.

Trust models between agents

When an agent receives instructions from another agent rather than directly from a human, how much trust should it extend? This question has no consensus answer in current practice, but several trust models have emerged:

Trust model Assumption Risk Used when
Full trust Instructions from any agent in the system are treated as authoritative as instructions from humans A compromised or manipulated orchestrator can instruct workers to take harmful actions they would otherwise refuse Internal closed systems with no external inputs
Capability-scoped trust An agent trusts instructions from other agents only within the receiving agent's declared capability scope Capability scope may be defined too broadly; agents may be instructed to do things that are technically within scope but contextually inappropriate Most production systems — the current best practice baseline
Policy-checked trust Every inter-agent instruction is checked against a policy engine before execution, regardless of source Latency overhead; policy engine becomes a single point of failure High-risk deployments, regulated industries, systems with external inputs
Zero trust No agent trusts any instruction from any other agent without human confirmation Eliminates the efficiency benefit of multi-agent systems entirely Theoretical baseline; rarely practical in production

The key insight is that in multi-agent systems, the attack surface expands with every agent added. Each inter-agent communication channel is a potential vector for prompt injection — an attacker who compromises one agent's context can potentially propagate malicious instructions to other agents in the system. Policy-checked trust is not theoretical caution; it is a practical requirement for systems that process external inputs.

Delegation chains and what they mean for accountability

In a typical multi-agent deployment, a human authorises an orchestrating agent to accomplish a goal. The orchestrating agent then delegates sub-tasks to worker agents. Those workers may, in turn, delegate to other workers. The result is a delegation chain of potentially significant depth.

Example delegation chain — invoice processing
Human (Finance Director) → Orchestrator (Claude) → Validator Agent → Payment Agent → Notification Agent
The Finance Director authorised the orchestrator. Did they authorise the payment agent to execute payments autonomously? What happens if the validator approves a fraudulent invoice?

The governance question is: at what point in this chain does human authority end, and what happens when a downstream agent takes an action the human would not have sanctioned? Three principles address this:

Scope inheritance: A delegating agent cannot grant a receiving agent more permissions than the delegating agent itself possesses. The payment agent cannot be authorised to make payments above a threshold that the orchestrator itself is not authorised to approve.

Accountability assignment: The human who authorised the orchestrator is accountable for everything the orchestrator delegates, whether or not they directly authorised each sub-task. This is the principal-agent accountability principle applied to AI systems.

Delegation depth limits: Governance frameworks should specify a maximum delegation depth. An action that requires three or more layers of delegation between the human authorisation and the execution is a sign that the system has more autonomy than the human can meaningfully oversee.

The distributed accountability problem

The most significant governance challenge in multi-agent systems is not technical — it is structural. When multiple agents collaborate to produce an outcome, it is often impossible to assign causal responsibility for that outcome to any single agent. The orchestrator did not write the bad recommendation; the research agent did, on the orchestrator's instruction, using data retrieved by the retrieval agent, in response to a prompt the user wrote.

This distributed causation does not dissolve accountability — it makes it harder to locate. The EU AI Act's approach is to assign accountability to the deployer, which is the organisation that put the system into use. The deployer is responsible for the system's outputs regardless of how complex the internal multi-agent architecture is. This is analogous to a company's vicarious liability for its employees' acts: the structure of internal delegation does not shield the organisation from external accountability.

For internal governance purposes, however, distributed accountability does create practical problems. Incident investigation in a multi-agent system requires logs that are attributable to individual agents — not just to the system as a whole. Without per-agent attribution, it is impossible to determine which agent introduced an error, which policy was violated, and where the governance control should have been placed.

Governance controls for multi-agent systems

Six controls matter most in production multi-agent deployments:

1. Per-agent identity and registration. Every agent in the system must have a distinct identity, a declared capability scope, a designated human sponsor, and a registered mission. An agent without a registered identity cannot be held accountable for its actions because there is no record that it existed as a governed entity.

2. Per-agent action logging. The audit trail must record which agent took which action, not merely which system produced which output. Without per-agent logging, incident investigation is impossible.

3. Policy-checked inter-agent communication. In high-risk deployments, instructions from one agent to another should be evaluated against a policy engine before the receiving agent executes them. This prevents orchestrator compromise from cascading to workers.

4. Scope inheritance enforcement. A technical control should prevent any agent from granting a downstream agent permissions the granting agent does not itself possess. This is not a human policy — it must be enforced by the governance infrastructure.

5. Delegation depth monitoring. The governance layer should alert when a task involves more delegation levels than the policy allows. Deep delegation chains are a governance warning sign.

6. Human escalation paths. Every multi-agent system should have documented escalation paths: conditions under which the system stops and routes to a human, and a designated human who is reachable when escalation occurs. The EU AI Act Article 14 requirement for human oversight applies to the deployed system, not just to individual agents within it.
